# Colors

Colour here is a **role**, never a hue. A component asks for
`--fm-color-primary-subtle-foreground` — "the ink that goes on the soft primary
wash" — and a theme decides what that is. That indirection is the whole point:
a rebrand moves a value in one stylesheet instead of every call site, and the
component keeps working because it never knew the colour in the first place.

There is no primitive ramp to reach past it. The contract exposes semantic roles
and nothing else, so there is no `blue-500` here to be tempted by.

Everything below is derived: the names come from `@fmmenchi/tokens`, and the
values are read out of the DOM in whichever theme is on screen. Use the
**Theme** toolbar — every swatch and every number on this page follows it,
because nothing here holds a copy of a value.

## The vocabulary

Every family is built from the same few words. Learn these six and you can read
any role in the system without looking it up.

| Role             | What it is                                      | Use it for                                                                              |
| ---------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------- |
| `base`           | The solid fill. The loudest form of the family. | A filled button, a solid badge, a filled progress bar. One per screen area, not five.   |
| `on base`        | The ink that sits **on** the solid fill.        | Label and icons inside that filled thing. Never as text on the page.                    |
| `subtle`         | The soft wash — same meaning, a tenth as loud.  | Alert backgrounds, chips, selected rows, anything that tints a region behind real text. |
| `on subtle`      | The ink that sits **on** the wash.              | Text inside the alert or the chip. It is dark where `on base` is light.                 |
| `border`         | The line at the edge of a subtle region.        | The rule around an alert. Status families only — an action family has hover instead.    |
| `hover`/`active` | The fill, darkened one and two steps.           | Pointer and pressed states of a `base` fill. Never a resting colour.                    |

Two rules that follow from the shape rather than from taste:

**An ink is only valid on its own fill.** `on base` is measured against `base`
and nothing else. Put it on the page background and the contrast guarantee in
the table below does not apply to it — most `on base` inks here are white.

**`base` and `subtle` are not light and dark versions of each other.** They are
two different jobs: `base` is a thing you press, `subtle` is a region you read
inside. Choosing between them is choosing whether the colour is the object or
the backdrop — which is why each has its own ink instead of sharing one.

`disabled` and `on disabled` mirror `base`/`on base` for the unavailable state,
and are the one pair exempt from the contrast floor (see below).

## The palette

There is no primitives file to show you, and that is a decision rather than an
omission. `vars.css` says it plainly: the values are static `oklch` literals
**resolved at authoring time** from the ramp methodology — base ± lightness,
scaled chroma. The ramp was applied when the numbers were chosen and never
became code, so there is no `blue-500` anywhere to import, and no primitive
layer to drift from the semantic one.

What can be shown is the palette that is actually shipped, reconstructed from
the values: every distinct colour, grouped by hue, ordered by lightness. It
cannot go stale, because it _is_ the tokens.

Each strip is named after the roles that live in that hue — `destructive ·
error`, not `hue 27°` — because the angle is where a colour sits, not what it
is for. The names are derived from the roles themselves, so nothing here is a
colour name somebody invented; the angle stays in the subtitle for when you
need it.

Under each swatch is its **lightness**, 0–100. A `·N` after it means **N roles
resolve to that exact value**: the 84 roles come out as far fewer colours, and
in the light theme a single value serves eleven of them. Hovering a swatch lists
every role that shares it.

The counts are the theme's own — a preset is a complete reassignment of every
role, so toggling redraws this whole section rather than re-tinting it. In light
the lightest shade is pure white and does most of that sharing; in dark it is
not, and the sharing lands elsewhere.

Two things this view makes visible that a list of roles cannot:

- the neutrals are by far the longest ramp, which is what a restrained system
  looks like from the inside;
- there are **two blues, ten degrees apart** — `info` sits at 245° while
  `primary`, `link`, `ring` and `selection` sit at 255°. It holds in both
  presets, and it is the kind of thing that is invisible until the palette is
  drawn.

## Action families

Four families for things a person can do — `primary`, `secondary`, `accent`,
`destructive` — each with the same eight roles: the solid fill, the ink on it,
hover and active, the subtle wash and its ink, and the disabled pair.

A family is complete or it is not a family: a theme that assigns six of the
eight has a component with nowhere to go on hover.

## Status families

`success`, `warning`, `info`, `error` — feedback, not action. They carry a
`-border` instead of hover and active states, because a status is something a
person reads, not something they press.

`error` and `destructive` are the same red and deliberately two roles: one is an
alert, the other is a button. Splitting them is what lets a destructive button
darken on press while an error message stays exactly as loud as it was.

## Surfaces, inputs and neutrals

What is left: the page and its cards, the input palette, the neutral and
disabled roles, and the single-purpose ones — `ring`, `scrim`, `selection`,
`link`, `tooltip`.

These are grouped by name prefix rather than by a list written here, so the
shape you see is the shape the contract has. Some come out as a pair, some as a
strip of one — and a strip of one is a colour that was needed once and named,
not a gap waiting to be filled.

## Contrast, measured

Every pair the contract declares, with the ratio measured live — the ink
painted on its own background and the two read back, so the number is the
browser's answer rather than this page's arithmetic.

The floor is **4.5**, WCAG 1.4.3 at AA for body text. Disabled pairs are marked
exempt: 1.4.3 excludes them, and they are shown anyway, because a number nobody
is allowed to hide is how you notice one that has drifted well past "low on
purpose".

An exempt pair is sampled as two tiles rather than as a line of text, and that
is not a cosmetic choice. The exemption covers the colours of a disabled
_control_; it does not cover this page painting real 1.38-contrast text in a
table. The first version did exactly that and axe failed the story — correctly,
which is the argument for running the a11y check on the documentation and not
only on the components.

This is not the gate. `tokens.test.ts` already fails the build on a pair that
drops below the floor, in both presets. What the table adds is the distance: a
pair that passes at 4.6 and one that passes at 12 are the same green tick to a
test and very different things to look at — and toggling the theme re-measures
every row.

The pairs are derived by rule (`role` has a partner when `role-foreground`
exists), which finds all of them but one: `background`/`foreground` are the page
itself, named before that convention existed. It is the only hand-stated pair
here.
