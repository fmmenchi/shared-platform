# Field

Groups a label, a control, and optional description/error text, and wires them for accessibility so
you don't hand-thread ids. Compose it: `<Field><FieldLabel/><Input/><FieldDescription/><FieldError/></Field>`.
It shares one id between the label's `htmlFor` and the control, registers the description and error
into the control's `aria-describedby`, and drives its `aria-invalid` from `invalid` — via React
context, so any transparent control inside picks the wiring up (the control's own props still win).
It owns no value or validation (ADR-0013) and has no chrome of its own — just layout and the text roles.

## Anatomy

- **`Field`** — the group; takes `invalid` and provides the context.
- **`FieldLabel`** — `<label>` tied to the control (click-to-focus, name-from-label).
- **`FieldDescription`** — helper text, added to `aria-describedby`.
- **`FieldError`** — the message; renders and joins `aria-describedby` **only when it has content**.
- **`useField()`** — prop getters for wiring a control the design system does not own.

`FieldDescription` and `FieldError` are shared with [Fieldset](?path=/docs/components-fieldset--docs):
they bind to the nearest container, so the same part describes this field's control here and a whole
group when placed directly inside a `Fieldset`.

## Wiring a control we don't own

The design system's controls pick the wiring up from context by themselves. A raw `<input>` or a
third-party control cannot — it never reads our context — so `useField()` hands the wiring over as prop
**getters**, which merge what you pass instead of replacing it:

```tsx
function BornOn({ locale }) {
  const { getLabelProps, getControlProps } = useField();
  return (
    <>
      <label {...getLabelProps()}>Born on</label>
      <ThirdPartyDatePicker {...getControlProps({ locale })} />
    </>
  );
}

<Field invalid={!!errors.bornOn}>
  <BornOn locale="it-IT" />
  <FieldError>{errors.bornOn}</FieldError>
</Field>;
```

One `useField()` counts as one control, so the "more than one control" guard keeps working. Called
outside a `Field` it warns and the getters pass your props through unchanged.

## Accessibility

- **Label association is automatic** — `FieldLabel htmlFor` and the control's `id` share one `useId`,
  so clicking the label focuses the control and the control's name comes from the label.
- **Description & error are announced with the field** — both register into `aria-describedby`, in
  **DOM order** (the registry sorts by document position, so a hint that appears later is still
  announced before the error it qualifies). Each renders only when it has content, so the control never
  references a blank element — and the parts own their ids, so an `id` passed to `FieldDescription` /
  `FieldError` is ignored rather than breaking the reference.
- **Invalid isn't colour alone** — `invalid` sets `aria-invalid` (announced) and the control shows a
  colour **and** a thicker border; the error text adds the words, and keeps a border rule under forced
  colors, where the hue is overridden to the system text colour.
- **A part used outside a `Field` warns by name** — a stray `FieldDescription` renders perfectly and
  describes nothing, which is invisible without the warning.
- **Announcing a fresh error is the consumer's job** — `FieldError` is described-by, not a live
  region. For an error that must be heard on submit, move focus to the field or use an error summary.
- **One control per Field.** The field owns a single `id`; put two controls in one `Field` and they
  collide (a dev warning fires). For a **radio/checkbox group** use a `<fieldset>` with a `<legend>`,
  not this single-control Field.
- **Precedence:** the field **owns the control's `id`** (so the label always associates — a control's
  own `id` is ignored inside a Field); `aria-describedby` **merges** the field's with the control's;
  the control's own `aria-invalid` **wins**.
- **The a11y ids resolve on the client.** The control itself renders server-side; the
  `aria-describedby` association is added on hydration (the description/error register via effect), so
  it's present for JS clients — not for no-JS delivery.
- **Only the design system's own controls auto-wire** (they call the internal field hook). A raw
  `<input>` or a third-party control won't pick the wiring up — set its `id`/`aria-describedby`
  yourself (a `FieldControl` slot for arbitrary elements is planned).
