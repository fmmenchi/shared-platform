# AppLayout

The page shell: the regions a product page is made of, and the things every product otherwise gets wrong about them.

```tsx
<AppLayout>
  <header>…</header>
  <AppLayoutNav label="Main">
    <Nav label="Main" orientation="vertical">
      …
    </Nav>
  </AppLayoutNav>
  <AppLayoutMain>…</AppLayoutMain>
  <aside>…</aside>
  <footer>…</footer>
</AppLayout>
```

## Anatomy

| part            | what it is                                                      |
| --------------- | --------------------------------------------------------------- |
| `AppLayout`     | the grid, the skip link, and the id the skip link points at     |
| `AppLayoutNav`  | the navigation region — a column above `@xl`, a drawer below it |
| `AppLayoutMain` | the page's one `<main>`, and the skip link's target             |

`<header>`, `<aside>` and `<footer>` are **your own elements**, not parts. They are landmarks with no behaviour, and a component around one would be an element that had not earned its place.

## Usage

<Canvas of={AppLayoutStories.Default} />

### It decides nothing about content

No brand, no user block, no icon set, no `items` array. The moment a shell takes a list of links it has invented a second markup language, and every product then needs one more field on it — which is why a ready-made sidebar belongs in the app that has a brand, not in a layer shared by products that do not.

### There is no `columns` prop

<Canvas of={AppLayoutStories.WithAside} />

The grid asks what is actually there. Add an `<aside>` and it is three columns; leave out `AppLayoutNav` and the content takes the whole width. An admin panel, a documentation site and a marketing page are the **same skeleton with different regions present** — naming them as three components would be three names for one grid, and the day one grew a prop the other lacked they would have stopped being it.

<Canvas of={AppLayoutStories.WithoutNav} />

### It answers to its own width, not the window's

The swap is a **container query**, which is the package's own stated order — a component adapts to its container before the viewport — and until this component nothing had exercised it: every other media query in the package asks about the _user's environment_ (forced colours, pointer, reduced motion), which no container can answer.

It also matters practically. A media query would hand a 16rem rail to a 380px panel, and a product whose breakpoint is not 48rem would have to override the rule — which a token cannot reach, because a media query cannot read a custom property. A container query asks the width the layout actually has, so a shell inside a narrow panel behaves narrow with nothing configured.

The swap point is the declared **`xl` container breakpoint** (48rem), reached through Tailwind's `@variant` — so it is compiled from the token rather than retyped. The condition itself cannot read a custom property (no media or container query can), but the value still has one home.

The cost is one element: a container query cannot interrogate the container it is written on, and every rule that decides this layout is a `grid-template-*` on the grid. So the outer element is the container and the inner one is the grid that asks it.

### The column becomes a drawer, and CSS still owns the breakpoint

Below the `xl` container breakpoint the navigation region is a `Dialog` pinned to the inline-start edge, with its own trigger; above it, a sticky column.

**One copy of the navigation**, moved between the two forms. The first version rendered both and let the stylesheet hide one, to keep the decision out of JavaScript — three reviews measured what that actually cost:

- crossing the breakpoint with the drawer **open** left a modal `<dialog>` with `display: none` on its wrapper: still `:modal`, still holding the scroll lock, still making the page inert, and with no box — so nothing could be clicked, focused or scrolled, and the close button did not exist. A dead page, reachable by rotating a tablet;
- every effect in the consumer's navigation ran **twice**, for ever;
- a consumer's own `id` inside it was duplicated, and `getElementById` resolved to the **hidden** copy — clicking a visible `<label>` focused nothing;
- and state diverged between the copies, so nothing survived the swap.

So JavaScript picks the form, but it is **not told the breakpoint**: the stylesheet sets `--nav-form` inside the same container query that lays the region out, and a `ResizeObserver` reads it back. One source of truth, still in CSS. Closing the drawer on the way to a column then needs no code — the dialog unmounts and `DialogContent` releases the scroll lock in its cleanup.

One consequence worth knowing: on a narrow screen, with the drawer shut, there is **no** navigation landmark on the page. That is the honest answer — the navigation is not on the page, it is behind a button. Its trigger is also not inside `<header>`, so a reader navigating by landmark will not meet it; if that matters for your product, render your own trigger inside the header and reach the dialog with `commandfor`.

### The two forms are not the same content

The shell swaps the **container**. What goes inside it is yours — and the two are rarely identical: a rail collapses to icons and a drawer does not, a drawer often carries a brand the header already shows on a wide screen, and on a phone it usually absorbs the account and search links that live in the header on desktop. Even the implementation this was modelled on passes `collapsible={false}` to its own drawer.

So the shell does not decide they are the same thing. It says which form is up:

```tsx
const form = useAppLayoutNavForm(); // 'column' | 'drawer' | null
```

and the same fact is on the region as `data-form`, for the many cases where the difference is only styling and no JavaScript is needed at all. Divergence is the exception, so `children` stays one slot and the ones who need it branch.

### A sticky header is the consumer's, and it covers things

If your `<header>` is sticky, set `--app-layout-header-offset` to its height on the layout. The shell cannot know it, and without it the sticky column's first link — and anything the browser scrolls to — lands underneath the banner, which is WCAG 2.4.11. The skip link needs no such help: it takes the top of the layer stack.

### Sizes are tokens, not props

`--fm-size-nav` and `--fm-size-aside` set the two columns. A sidebar's width is a measurement, so a theme retunes it exactly the way it retunes a colour; an API taking pixels would have to anticipate every product that ever asks.

## Accessibility

- **A skip link, first** (WCAG 2.4.1) — invisible until it has the focus, and then unmistakably there. `AppLayoutMain` carries `tabindex="-1"` so following it **moves the focus**, which is the half a skip link usually gets wrong: the browser scrolls and leaves the focus behind, so the next `Tab` returns the reader to the navigation they just skipped.
- **The id is the shell's**, not yours. A skip link pointing at an id nobody set goes nowhere, and says nothing while doing it.
- **One `<main>`, one `<header>`, one `<footer>`** — the landmark set is the structure, and the regions are placed by what they are.
- **The drawer is a modal dialog**, so it brings the focus trap, the inert page and the scroll lock with it; it is named from `label`, because a `<dialog>` with no accessible name is announced as just "dialog".
