# AppLayout

The page shell: the regions a product page is made of, and the things every product otherwise gets wrong about them.

```tsx
<AppLayout>
  <header>…</header>
  <AppLayoutNav label="Main">
    <Nav label="Main" orientation="vertical">
      …
    </Nav>
  </AppLayoutNav>
  <AppLayoutMain>…</AppLayoutMain>
  <aside>…</aside>
  <footer>…</footer>
</AppLayout>
```

## Anatomy

| part                 | what it is                                                     |
| -------------------- | -------------------------------------------------------------- |
| `AppLayout`          | the grid, the skip link, and the id the skip link points at    |
| `AppLayoutNav`       | the navigation region — it owns the swap between the two forms |
| `AppLayoutNavColumn` | what the navigation is as a column, above `@xl`                |
| `AppLayoutNavDrawer` | what it is inside the drawer, below `@xl`                      |
| `AppLayoutMain`      | the page's one `<main>`, and the skip link's target            |

`<header>`, `<aside>` and `<footer>` are **your own elements**, not parts. They are landmarks with no behaviour, and a component around one would be an element that had not earned its place.

## Usage

<Canvas of={AppLayoutStories.Default} />

### It decides nothing about content

No brand, no user block, no icon set, no `items` array. The moment a shell takes a list of links it has invented a second markup language, and every product then needs one more field on it — which is why a ready-made sidebar belongs in the app that has a brand, not in a layer shared by products that do not.

### There is no `columns` prop

<Canvas of={AppLayoutStories.WithAside} />

The grid asks what is actually there. Add an `<aside>` and it is three columns; leave out `AppLayoutNav` and the content takes the whole width. An admin panel, a documentation site and a marketing page are the **same skeleton with different regions present** — naming them as three components would be three names for one grid, and the day one grew a prop the other lacked they would have stopped being it.

<Canvas of={AppLayoutStories.WithoutNav} />

### It answers to its own width, not the window's

The swap is a **container query**, which is the package's own stated order — a component adapts to its container before the viewport — and until this component nothing had exercised it: every other media query in the package asks about the _user's environment_ (forced colours, pointer, reduced motion), which no container can answer.

It also matters practically. A media query would hand a 16rem rail to a 380px panel, and a product whose breakpoint is not 48rem would have to override the rule — which a token cannot reach, because a media query cannot read a custom property. A container query asks the width the layout actually has, so a shell inside a narrow panel behaves narrow with nothing configured.

The swap point is the declared **`xl` container breakpoint** (48rem), reached through Tailwind's `@variant` — so it is compiled from the token rather than retyped. The condition itself cannot read a custom property (no media or container query can), but the value still has one home.

The cost is one element: a container query cannot interrogate the container it is written on, and every rule that decides this layout is a `grid-template-*` on the grid. So the outer element is the container and the inner one is the grid that asks it.

### The column becomes a drawer, and CSS still owns the breakpoint

Below the `xl` container breakpoint the navigation region is a `Dialog` pinned to the inline-start edge, with its own trigger; above it, a sticky column.

**One copy of the navigation**, moved between the two forms. The first version rendered both and let the stylesheet hide one, to keep the decision out of JavaScript — three reviews measured what that actually cost:

- crossing the breakpoint with the drawer **open** left a modal `<dialog>` with `display: none` on its wrapper: still `:modal`, still holding the scroll lock, still making the page inert, and with no box — so nothing could be clicked, focused or scrolled, and the close button did not exist. A dead page, reachable by rotating a tablet;
- every effect in the consumer's navigation ran **twice**, for ever;
- a consumer's own `id` inside it was duplicated, and `getElementById` resolved to the **hidden** copy — clicking a visible `<label>` focused nothing;
- and state diverged between the copies, so nothing survived the swap.

So JavaScript picks the form, but it is **not told the breakpoint**: the stylesheet sets `--nav-form` inside the same container query that lays the region out, and a `ResizeObserver` reads it back. One source of truth, still in CSS. Closing the drawer on the way to a column then needs no code — the dialog unmounts and `DialogContent` releases the scroll lock in its cleanup.

One consequence worth knowing: on a narrow screen, with the drawer shut, there is **no** navigation landmark on the page. That is the honest answer — the navigation is not on the page, it is behind a button. Its trigger is also not inside `<header>`, so a reader navigating by landmark will not meet it.

There is no workaround to offer yet: the drawer's surface id is internal, so a second trigger of your own cannot reach it with `commandfor`, and building your own `Dialog` beside this one is the duplicate-navigation defect the component exists to prevent. Putting the few links a phone most needs in your `<header>` as well is the only thing that helps today.

### The two forms are not the same content

The shell swaps the **container**. What goes inside it is yours — and the two are rarely identical: a rail collapses to icons and a drawer does not, a drawer often carries a brand the header already shows on a wide screen, and on a phone it usually absorbs the account and search links that live in the header on desktop. Even the implementation this was modelled on passes `collapsible={false}` to its own drawer.

So the shell does not decide they are the same thing. It gives each form **its own slot**, and keeps the swap:

```tsx
<AppLayoutNav label="Main">
  <AppLayoutNavColumn>
    <Nav label="Main" orientation="vertical">
      …
    </Nav>
  </AppLayoutNavColumn>
  <AppLayoutNavDrawer>
    <Nav label="Main" orientation="vertical">
      …
    </Nav>
    {/* Not extra destinations: the ones the header carries on a wide
        screen, brought down here because a phone's header has no room. */}
    <AccountLinks />
  </AppLayoutNavDrawer>
</AppLayoutNav>
```

<Canvas of={AppLayoutStories.DivergentForms} />

Only the form in play is rendered, so the slot that is not up leaves nothing behind — no hidden element, no duplicated `id`, no state to diverge.

**Nothing at all is rendered until `--nav-form` has been read**, which is the whole of the first render and costs nothing on screen: the ref callback runs during the commit, so its re-render lands before the paint. The version before this guessed `drawer` and corrected itself, and the guess was not free — with a single slot, or with the loose children recommended just below for the simple case, the content that ends up on a wide screen was mounted first inside the dialog and then again in the flow. Two mounts, so two of every fetch in it: a halved copy of the defect above.

What it costs instead, plainly: a server-rendered page ships an **empty region**. Little is actually lost, because the version that guessed shipped a wide page's navigation inside a closed `<dialog>` — `display: none` — which a reader without JavaScript could not see either.

One thing "rendered" still does **not** mean: a **closed `<dialog>` holds its subtree**, so on a narrow screen the drawer's contents are mounted from the first render even if nobody opens it. If what you put in it fetches, it fetches on load.

**Give one slot and it serves both forms**; give none and `children` does, which keeps the simple case one line long. The **container** always follows the form and only the contents fall back — otherwise the shorthand for "my two forms are the same" would put a 16rem rail on a phone. Passing the same element to both slots is your business, and free.

A slot has to be a **direct child**. `AppLayoutNav` finds it by type, and what is inside a component of your own — or a `<Suspense>`, or a `React.lazy` — does not exist until that component renders, so no amount of walking would reach it. Fragments are the one exception and are looked through: `React.Children` does not flatten them, and the first version of this rendered an empty navigation for `<><AppLayoutNavColumn/><AppLayoutNavDrawer/></>` without complaining.

Every other wrapper still produces an empty navigation — it cannot produce anything else — but no longer a silent one: a slot that is **rendered** knows it was never read, and says so in development. That is the only place the mistake is visible, since the region sees an element of a type it does not recognise and cannot tell a wrapper from any other child.

Two more resolutions, both loud for the same reason:

- **children beside a slot are dropped.** Once either slot is present, everything the navigation renders has to be inside one of them;
- **a slot given twice keeps the first.**

And every way of spelling _empty_ — `null`, `false`, `[]`, `''` and `undefined` — means **given, and deliberately empty**, not "not given". `undefined` used to be the odd one out, which made `{user ? <Nav/> : undefined}` hand a logged-out phone the desktop rail it had explicitly asked not to have.

When the difference is only styling, no slot is needed at all — the form is on the region as `data-form`, and in JavaScript:

```tsx
const form = useAppLayoutNavForm(); // 'column' | 'drawer' | null
```

### A sticky header is the consumer's, and it covers things

If your `<header>` is sticky, two lines — both yours, because both touch things the shell has no
authority over (ADR-0022):

```css
:root {
  --app-layout-header-offset: 64px; /* your banner's height */
}
html {
  scroll-padding-block-start: var(--app-layout-header-offset);
}
```

The variable offsets the sticky column; the `html` rule is what keeps **anything the browser scrolls
to** — an anchor jump, a Shift+Tab to a control above the fold — from landing underneath the banner
(WCAG 2.4.11). It has to live on `html` because the _document_ is what scrolls: an earlier version
declared `scroll-padding` on the layout's own grid, where the property is inert by definition. The
skip link needs no such help: it takes the top of the layer stack.

### Sizes are tokens, not props

`--fm-size-nav` and `--fm-size-aside` set the two columns. A sidebar's width is a measurement, so a theme retunes it exactly the way it retunes a colour; an API taking pixels would have to anticipate every product that ever asks.

## Accessibility

- **A skip link, first** (WCAG 2.4.1) — invisible until it has the focus, and then unmistakably there. `AppLayoutMain` carries `tabindex="-1"` so following it **moves the focus**, which is the half a skip link usually gets wrong: the browser scrolls and leaves the focus behind, so the next `Tab` returns the reader to the navigation they just skipped.
- **The id is the shell's**, not yours. A skip link pointing at an id nobody set goes nowhere, and says nothing while doing it.
- **One `<main>`, one `<header>`, one `<footer>`** — the landmark set is the structure, and the regions are placed by what they are.
- **The drawer is a modal dialog**, so it brings the focus trap, the inert page and the scroll lock with it; it is named from `label`, because a `<dialog>` with no accessible name is announced as just "dialog".
- **The drawer must be a superset of the column** for anything not reachable elsewhere on the page (WCAG 1.4.10, Reflow). Two slots make dropping a link at 320px a one-line mistake, and the swap is a _container_ query — so it is not only phones: a desktop reader at 200% zoom, or in a split pane, is on the drawer side of it too. Leaving links out of the **column** is the safe direction, and only when the header carries them.
- **Divergence has to stay consistent** (WCAG 3.2.3): the same destinations in the same relative order, minus what the other form's header already shows. Curating is fine; re-ordering the same list between forms is what makes a reader relearn the page at every breakpoint.
- **`aria-current="page"` belongs in both slots.** Set in one only, the current page is unmarked for whoever meets the other form.
- **Focus survives the swap.** A `<dialog>` removed rather than closed fires no `close` event, so the browser's own restoration never runs and the focus would land on `<body>`: rotate a tablet with the drawer open and the next `Tab` would start again from the skip link. The region catches that and moves the focus to the first thing in the form that replaced it — and only then, never when the focus was somewhere else on the page.
