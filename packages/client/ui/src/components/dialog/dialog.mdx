# Dialog

Dialog is something the user must deal with before going back to the page: the background is inert, the focus is trapped inside, and it is dismissed on purpose.

```tsx
<Dialog>
  <DialogTrigger>Delete…</DialogTrigger>
  <DialogContent>
    <DialogHeading>Delete this draft?</DialogHeading>
    <p>It cannot be undone.</p>
    <DialogClose>Cancel</DialogClose>
  </DialogContent>
</Dialog>
```

If it can be ignored, it is a `Popover`. If it only describes its trigger, it is a `Tooltip`.

## Anatomy

```tsx
<Dialog>
  {' '}
  {/* wiring: no element of its own */}
  <DialogTrigger /> {/* a <button>: command="show-modal" */}
  <DialogContent>
    {' '}
    {/* the native <dialog>, opened modally */}
    <DialogHeading /> {/* the dialog's accessible name */}
    …
    <DialogClose /> {/* command="close" */}
  </DialogContent>
</Dialog>
```

| part            | what it is                                                                                       |
| --------------- | ------------------------------------------------------------------------------------------------ |
| `Dialog`        | the wiring. It renders **no element** — one that only carries a context has not earned its place |
| `DialogTrigger` | what opens it: `command="show-modal"`, no handler                                                |
| `DialogContent` | the dialog itself — a native `<dialog>`, opened modally, in the top layer                        |
| `DialogHeading` | names it. An `h2` by default, `as` for the level the page needs                                  |
| `DialogClose`   | closes it from inside. It exists because the dialog's id is generated and internal               |

`DialogTrigger` and `DialogClose` take a `Button`'s props — including `variant` — and an `as` for anything that accepts them and ends in a `<button>`, which is what `commandfor` requires. `DialogHeading` takes an `as` restricted to the six heading levels, because it names the dialog.

### What is not in here

The list is longer than the component. Measured in Chromium, Firefox and WebKit before a line of it was written:

| what a dialog needs         | who does it                                                 |
| --------------------------- | ----------------------------------------------------------- |
| open it                     | `command="show-modal"` — no handler, works before hydration |
| trap the focus              | `showModal()`                                               |
| make the page behind inert  | `showModal()`                                               |
| the dimmed backdrop         | `::backdrop`                                                |
| dismiss on `Escape`         | the platform                                                |
| dismiss on a backdrop click | `closedby="any"`                                            |
| close it from inside        | `command="close"`                                           |
| return a value              | `<form method="dialog">` → `dialog.returnValue`             |
| **stop the page scrolling** | **one CSS rule**, `:root:has(…[open]) { overflow: hidden }` |
| **put the focus back**      | the platform — except WebKit, which we repair               |

That last pair is everything this component adds. The scroll lock is where libraries reach for a dependency (`react-remove-scroll`) and a backdrop-click handler that compares click coordinates to the dialog's box; `:has()` and `closedby` replace both.

### Scrolling, and the scrollbar

A modal that lets the page scroll behind it is the commonest defect of the pattern, and `showModal()` does not prevent it — measured, the page scrolled 300px under an open dialog in all three engines. One rule does, scoped to this component's own dialog so it never speaks for somebody else's.

What it deliberately does **not** do is compensate for the scrollbar it hides. On a platform with classic scrollbars, fixed elements shift by its width when the lock engages — measured at 15px, and `scrollbar-gutter: stable` did not cure it. That compensation is a page-level decision and the design system ships no page rules (ADR-0022): if it matters to your app, reserve the gutter on your own `:root`.

## Accessibility

- **A native `<dialog>`, named by its heading.** The role comes from the element (ADR-0016); `DialogHeading` registers its id as `aria-labelledby`. A dialog with no name is announced as "dialog" and nothing else.
- **The trigger says what will appear** — `aria-haspopup="dialog"` — and deliberately **not** `aria-expanded`: unlike a popover's trigger, this one is inert while the dialog is open, so "expanded" would describe a state nobody can observe from it.
- **The focus is trapped by the platform**, and the ring is not identical in every engine — Chromium passes through the document on its way round, WebKit lands on the dialog itself. What holds everywhere is the thing that matters: nothing outside is reachable.
- **The focus comes back.** Chromium and Firefox return it to the trigger; WebKit drops it on `<body>`, so the component puts it back — only ever a repair, never a second guess when the engine already did the right thing.
- **`Escape` always works**, in every engine, with or without `closedby`.

### Where it is painted

In the **top layer**, like the other surfaces, which is why it needs no `z-index` and no portal — and why the backdrop can exist at all.
