# Dialog

Dialog is something the user must deal with before going back to the page: the background is inert, the focus is trapped inside, and it is dismissed on purpose.

```tsx
<Dialog>
  <DialogTrigger>Delete…</DialogTrigger>
  <DialogContent>
    <DialogHeading>Delete this draft?</DialogHeading>
    <p>It cannot be undone.</p>
    <DialogClose>Cancel</DialogClose>
  </DialogContent>
</Dialog>
```

If it can be ignored, it is a `Popover`. If it only describes its trigger, it is a `Tooltip`.

## Anatomy

```tsx
<Dialog>
  {' '}
  {/* wiring: no element of its own */}
  <DialogTrigger /> {/* a <button>: command="show-modal" */}
  <DialogContent>
    {' '}
    {/* the native <dialog>, opened modally */}
    <DialogHeading /> {/* the dialog's accessible name */}
    …
    <DialogClose /> {/* command="close" */}
  </DialogContent>
</Dialog>
```

| part            | what it is                                                                                       |
| --------------- | ------------------------------------------------------------------------------------------------ |
| `Dialog`        | the wiring. It renders **no element** — one that only carries a context has not earned its place |
| `DialogTrigger` | what opens it: `command="show-modal"`, no handler                                                |
| `DialogContent` | the dialog itself — a native `<dialog>`, opened modally, in the top layer                        |
| `DialogHeading` | names it. An `h2` by default, `as` for the level the page needs                                  |
| `DialogClose`   | closes it from inside. It exists because the dialog's id is generated and internal               |

`DialogTrigger` and `DialogClose` take a `Button`'s props — including `variant` — and an `as` for anything that accepts them and ends in a `<button>`, which is what `commandfor` requires. `DialogHeading` takes an `as` restricted to the six heading levels, because it names the dialog.

### What is not in here

The list is longer than the component. Measured in Chromium, Firefox and WebKit before a line of it was written:

| what a dialog needs         | who does it                                                 |
| --------------------------- | ----------------------------------------------------------- |
| open it                     | `command="show-modal"` — the attribute is the behaviour     |
| trap the focus              | `showModal()`                                               |
| make the page behind inert  | `showModal()`                                               |
| the dimmed backdrop         | `::backdrop`                                                |
| dismiss on `Escape`         | the platform                                                |
| dismiss on a backdrop click | `closedby="any"`                                            |
| close it from inside        | `command="close"`                                           |
| return a value              | `<form method="dialog">` → `dialog.returnValue`             |
| **stop the page scrolling** | **one CSS rule**, `:root:has(…[open]) { overflow: hidden }` |
| **put the focus back**      | the platform — except WebKit, which we repair               |

That last pair is everything this component adds. The backdrop-click handler that compares click coordinates to the dialog's box — the one every library writes — is replaced by `closedby` outright.

The scroll lock is written **inline on `:root`**, not as a stylesheet rule, and that is a correction rather than a preference: as a rule inside `@layer fmmenchi` it was beaten by an ordinary unlayered `html { overflow-y: auto }` on the consumer's page, so the modal opened over a page that still scrolled — ADR-0022 had already rejected that shape for exactly this reason. It also keys on `:modal`, not on the `open` attribute: a non-modal `<dialog open>` leaves the page interactive, and freezing its scroll would trap the user with nothing to dismiss.

### Opening it from code

Uncontrolled is the default and the one to reach for: leave `open` out and the state lives in the DOM, where the browser put it. `defaultOpen` seeds it once at mount, and `onOpenChange` reports what happened, whoever caused it.

`open` is there for when the dialog's visibility is genuinely part of your state, and it is a commitment rather than a convenience. It is the source of truth while it is given, so it wins BACK: a dialog the platform closed while the prop still says open is reopened. And this dialog is closed by the browser **four** ways that never ask React — `Escape`, a backdrop click under `closedby="any"`, `<form method="dialog">` and `command="close"` — so `open` without `onOpenChange` builds a modal the user cannot dismiss. That combination warns in development, as does switching between controlled and uncontrolled halfway through.

Both halves are imperative underneath, and that is forced: `<dialog open>` is a **non-modal** dialog — no backdrop, the page behind stays clickable, `Escape` does not close it — so modality can only be asked for with `showModal()`. The component calls it for you; you can still call it yourself through the content's ref.

### A drawer is this component with a side

<Canvas of={DialogStories.Drawer} />

`side` pins the surface to an edge instead of centring it, which is the whole of what a drawer is here. There is no second family, and that is deliberate: `showModal()` traps the focus, makes the page inert and draws the backdrop, and this component adds the scroll lock and the focus-return repair on top of it — a drawer wants every one of those unchanged. What differs is geometry, so the prop is geometry.

```tsx
<DialogContent side="inline-start" aria-label="Navigation menu">
  <DialogClose>Close</DialogClose>
  <Nav label="Main" orientation="vertical">
    …
  </Nav>
</DialogContent>
```

The edges are **logical**: `inline-start` is the left in English and the right in Arabic, and the panel both pins and slides in from that side either way. `block-end` puts it along the bottom, where a phone expects a sheet.

Four things to know:

- **name it.** A drawer usually shows no heading — a navigation one is a list of links — and a `<dialog>` with no accessible name is announced as just "dialog". `aria-label` on the content is enough, and the component warns in dev when neither that nor `aria-labelledby` is there.
- **give it a close control.** Not one option of three: the APG asks for a visible one in every modal, and on a phone it is the only one of the three that exists. There is no `Escape` key there, and the backdrop depends on `closedby` — Baseline "newly", and switchable off with `closedby="none"`.
- **close it yourself when a link is chosen.** `NavLink` adds no handler, because a link is the one control the browser does perfectly — so with a client router the route changes underneath and the drawer stays open over the page it just navigated to. One handler on the nav does it; the story shows it.
- **no swipe to dismiss.** The platform offers no gesture for it and this package ships no gesture engine.

### Scrolling, and the scrollbar

A modal that lets the page scroll behind it is the commonest defect of the pattern, and `showModal()` does not prevent it — measured, the page scrolled 300px under an open dialog in all three engines. One rule does, scoped to this component's own dialog so it never speaks for somebody else's.

It compensates for the scrollbar it hides, as far as anything can. Hiding the overflow widens the viewport by the scrollbar's width, so the page's content jumps sideways; the lock pads the root by the width it measured, which holds the content in the flow still. Elements positioned `fixed` still move, and nothing written from here can prevent that — `react-remove-scroll` has the same limitation for the same reason.

Measured with a classic scrollbar, the shift is 15px in WebKit, and `scrollbar-gutter: stable` does **not** cure it there even though the engine reports the property as supported. On Chromium it does. There is no remedy that works everywhere; this is the honest state of it, not an omission.

## Accessibility

- **A native `<dialog>`, named by its heading.** The role comes from the element (ADR-0016); `DialogHeading` registers its id as `aria-labelledby`. A dialog with no name is announced as "dialog" and nothing else.
- **The trigger says what will appear** — `aria-haspopup="dialog"` — and deliberately **not** `aria-expanded`: unlike a popover's trigger, this one is inert while the dialog is open, so "expanded" would describe a state nobody can observe from it.
- **The focus is trapped by the platform**, and the ring is not identical in every engine — Chromium passes through the document on its way round, WebKit lands on the dialog itself. What holds everywhere is the thing that matters: nothing outside is reachable.
- **The focus comes back.** Chromium and Firefox return it to the trigger; WebKit drops it on `<body>`, so the component puts it back — only ever a repair, never a second guess when the engine already did the right thing.
- **`Escape` always works**, in every engine, with or without `closedby`.
- **It says so when it is misused.** In development it warns if the dialog has no accessible name, and if the trigger renders anything other than a `<button>` — `commandfor` works on nothing else, so such a trigger is silently dead, and only on the browsers that have invoker commands.

### Before hydration, and the attribute that has to be there

The trigger carries `command`/`commandfor` **always**, on the server as well as in the browser, and a click handler stands by for browsers that do not have invoker commands yet — it asks the question at click time rather than when the module loads. That sounds like a detail and is not: the first version answered it once, at module scope, where the answer on a server is "no DOM". The attribute never reached the server HTML, React declined to patch it in ("This won't be patched up"), and the fallback stood down because on the client the answer had flipped. The dialog was dead for every SSR consumer.

### Where it is painted

In the **top layer**, like the other surfaces, which is why it needs no `z-index` and no portal — and why the backdrop can exist at all.
