# FormErrorSummary

After a failed submit, one place that says what went wrong and takes you to each field.

```tsx
<FormErrorSummary labelFor={(name) => LABELS[name]} />
```

It renders **nothing** while the form is valid, so it can sit in the markup unconditionally.

## Why the adapter has a form level at all

A per-field message is announced only once you reach that field. On a long form, a keyboard or
screen-reader user has no way to learn that three fields failed without walking the whole thing —
and no way to find them again afterwards. The summary is the fix, and it needs **errors keyed by
name**, which no single field can provide. That is the entire reason `UseFormStatus` exists.

## Accessibility

- **It takes focus when it appears, and on every failed submit after that**, so the failure is
  announced immediately rather than waiting to be discovered — and so a resubmission that is rejected
  again is never silent. Those two edges are the whole trigger; the error _count_ is not, because a
  library that revalidates as you type drops it the moment a field becomes valid, and focus must not
  leave the input you are still typing in.
- **A labelled `role="group"`, not `role="alert"`.** Focusing the summary already announces it, where
  an alert would announce it a second time from wherever you happened to be. Note that `group` is not
  a landmark role, so the summary does not appear in a landmark rotor.
- **Each entry moves focus to its control.** Fields carry generated ids, so the link cannot point at
  one; the field **name** is the stable handle, and it is what the form library and the DOM already
  agree on.
- **`labelFor` is not decoration.** Without it the list shows the raw `name` — `given_name`,
  `tos` — which is a database column, not something a person recognises.
- Every message from every field is listed, in field order, so a field failing three rules produces
  three entries rather than one summary of a summary.
