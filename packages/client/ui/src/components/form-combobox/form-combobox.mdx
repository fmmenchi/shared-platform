# FormCombobox

A labelled [`Combobox`](?path=/docs/components-inputs-combobox--docs) already
bound to the form library in scope. It names nothing about that library, and it
puts the binding on the node that carries the value rather than the one you type
in.

## Usage

```tsx
<UiProvider adapters={{ i18n, form: { field, errors } }}>
  <FormCombobox
    name="city"
    label="City"
    items={cities}
    getKey={(c) => c.id}
    getLabel={(c) => c.name}
  />
</UiProvider>
```

### Several of many, bound

```tsx
<FormCombobox
  multiple
  name="cities"
  label="Cities"
  items={cities}
  getKey={(c) => c.id}
  getLabel={(c) => c.name}
/>
```

`multiple` binds through a **different port** — the option field, not the per-field
one — and that is the whole difference rather than a detail. One value is one
control with one bag of props; a set is N carriers under one name, and only the
option port can say a whole list.

It matters because **a removal is the absence of an element, so it has nobody to
send an event for it**. Measured across five bindings: the two that read the
document at submit were exact, and the three that keep a store were told when a
carrier arrived and never told when one left — so the value kept a key the reader
had removed. The field says its whole value instead (`setValues`), and the
carriers went back to drawing it.

The starting selection comes from the **library**, not from the call site: the
binding is asked, once at mount, which of the items it already holds. So a form
whose `defaultValues` name two cities opens with those two tags.

### Declare it in your field types

```ts
createConformField({ types: { city: 'combobox' } });
```

`'combobox'` is not an `<input>` type. It tells the binding that the field it
sees is the component's **carrier** — a text input holding the chosen key — so
Conform reaches for its `<input>` helper rather than the `<select>` or
`<textarea>` one.

It does **not** keep a schema-derived `pattern`, `multiple` or `maxLength` off
that key: Conform emits those from the constraint whatever type it is handed.
Dropping them is `FormCombobox`'s own routing table, which is why the binding is
never spread blindly onto the control.

## Accessibility

- **The label is associated**, which the bare `Combobox` cannot do for itself:
  the wrapper's `Field` supplies the id the label points at, the
  `aria-describedby` the hint and error register into, and `aria-invalid`.
- Everything else is the control's own — see
  [`Combobox`](?path=/docs/components-inputs-combobox--docs) for the combobox
  pattern, the live region and the coarse-pointer shape.

## Guidelines

### Two refs, two jobs, two nodes

The binding's ref goes to the **carrier**; your `ref` goes to the visible field.
That is not tidiness: a form library reads `.value` off the element its ref was
given, and given the visible input it would read the **search text** rather than
the chosen key. The same applies to `onChange` and `onBlur`, which the control
routes to the carrier for the same reason — what the user types is reported by
`onQueryChange`.

### What the binding owns never comes from the call site

`value`, `defaultValue`, `checked` and `onChange` are the binding's. Passing one
here would not override the binding, it would sever it — so they are refused by
the type and warned about at runtime.
