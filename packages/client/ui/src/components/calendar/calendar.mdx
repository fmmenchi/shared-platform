# Calendar

A month of days, for picking one.

It exists for **one** thing the platform does not offer and will not:
**per-date disabling**. `min`/`max` on a native date input are an interval, not a
set, so "only these slots", "never on a Tuesday", "these three days are booked"
cannot be said to it at all (ADR-0027). `isDateDisabled` is a predicate.

If you do not need that, you do not need this: `DateInput` is one tag and no
keyboard of ours.

## Usage

### The reason it exists

<Canvas of={Stories.PerDateRules} />

`isDateDisabled` is asked about every day the grid draws. A refused day keeps its
place and stays reachable by the arrows — it is `aria-disabled`, not `disabled`,
which is the APG's "focusable but not activatable". A day the arrows skipped
would be a day a screen-reader user is never told about.

### What it hands back

<Canvas of={Stories.ReadingTheValue} />

A `CivilDate` — `{ year, month, day }`, months **1–12** — and never a `Date`. A
`Date` is an instant; a day on a calendar is not. `new Date('2026-08-12')` is the
11th of August in every timezone west of Greenwich, which is the defect this
whole family exists to stop repeating.

**The selection is controlled or uncontrolled, and here React holds it** — unlike
every field in this package, and for the opposite reason: there is no `<input>`
under a calendar for the browser to keep a value in.

### The picker

<Canvas of={Stories.InsideAPopover} />

The shape most consumers actually want — and if it is what you want, reach for
[DatePicker](?path=/docs/components-inputs-datepicker--docs), which is this
composition done once and correctly. What follows is what it does inside, and
what to write when you need a shape it does not offer.

```tsx
const carrier = useRef<HTMLInputElement>(null);

<DateInput
  name="departure"
  carrierRef={carrier}
  onDateChange={take}             // ← the field tells the calendar
/>
<Popover open={open} onOpenChange={setOpen}>
  <PopoverTrigger aria-label="Pick a date">📅</PopoverTrigger>
  <PopoverContent>
    <Calendar
      value={picked}
      month={month}
      onMonthChange={setMonth}
      onValueChange={(date) => {
        setPicked(date);
        writeDateInput(carrier.current, date);   // ← the calendar sets the field
        setOpen(false);
      }}
    />
  </PopoverContent>
</Popover>
```

**Three pieces of state, three different owners, and that is the design.** The
date lives in the DOM, on the carrier, as it does for every control here. The
calendar's highlight lives in React, because a grid has no DOM home for it. The
popover's open state lives in React only so that picking a day can close it.

**Both directions are wired, and the second one is easy to forget.** Without
`onDateChange`, a date TYPED into the field never reaches the calendar — reopen
the popover and it highlights the day chosen three edits ago, which the field no
longer holds.

**And the month travels with the value.** This is the piece most likely to be
left out, and the calendar will not do it for you: a date typed in December 2027
lands on a day an August 2026 grid does not draw, so the popover opens with
nothing selected in it.

```tsx
const [picked, setPicked] = useState(null);
const [month, setMonth] = useState(AUGUST);

// The piece consumers leave out, written out rather than glossed.
const take = (date) => {
  setPicked(date);
  if (date !== null) setMonth(date);
};

<DateInput onDateChange={take} … />
<Calendar value={picked} month={month} onMonthChange={setMonth} … />
```

That the calendar does not follow its own `value` is a decision. Following it
from inside means writing state in an effect on every value change, which then
fights the navigation the user just made — and the tab stop has to move with it,
which is a plain `useState` setter and exactly what the `react-hooks` lint
refuses in an effect body. Only the thing holding both knows whether the value
moved BECAUSE of the grid or in spite of it.

The calendar does put the tab stop on the **selected** day when the month moves
under it, so the arrows start where the eye does — that part it can derive
without state, and it is the half a composition cannot supply, there being no
`focused` prop to hand it.

**The calendar sets the field; it does not replace it.** The field is still a
field afterwards — it can be typed into, it still holds the value, and it is
still what the form posts.

`writeDateInput` takes the node `carrierRef` gives you and writes it exactly as
a keystroke does: the prototype setter, so React's value tracker is left stale
and hears the change, then a bubbling `input` event, so the field redraws and a
form binding learns about it. A plain `carrier.value = …` would update the DOM
and tell nobody. `null` clears the field.

There is no `value` prop to hand `DateInput` instead: the browser owns that value
(ADR-0013), and `defaultValue` stops reaching the DOM the moment the user has
typed. Writing the DOM is the honest way in.

**`PopoverTrigger` is itself a `Button`** — do not nest one inside it, or a
keyboard user meets two tab stops for one affordance.

### Locale

<Canvas of={Stories.AcrossLocales} />

The month name, the weekday names and **the day a week starts on** all come from
the locale you gave `UiProvider` — the same one `DateInput` and `Time` read.
`firstDayOfWeek` overrides it when a consumer knows better; its default is what
`Intl.Locale.prototype.getWeekInfo()` reports, and Monday where that is missing.
That API is Baseline Newly and ships in two incompatible shapes, which is
survivable precisely because it degrades: without it the grid still works and the
week simply starts somewhere else.

## Keyboard

The APG grid contract, and the whole of what makes a calendar hard.

| Key                                   | Moves                   |
| ------------------------------------- | ----------------------- |
| <kbd>←</kbd> <kbd>→</kbd>             | one day                 |
| <kbd>↑</kbd> <kbd>↓</kbd>             | one week                |
| <kbd>Home</kbd> <kbd>End</kbd>        | to the ends of the week |
| <kbd>PageUp</kbd> <kbd>PageDown</kbd> | one month               |
| <kbd>Shift</kbd> + those Page keys    | one year                |
| <kbd>Enter</kbd> <kbd>Space</kbd>     | chooses the day         |

**The roving focus is a date, not a cell.** Any of those moves can cross into a
month that is not on screen, which replaces every cell in the grid — so the
component holds the focused _day_ and puts focus on whichever cell then carries
it. A cell index would name a different day after every such move.

A month is **one tab stop**, not forty-two: Tab reaches the grid and the arrows
do the rest.

`PageDown` from the 31st **clamps** to the end of the month it lands in — 31
January plus a month is 28 February, not 3 March. Rolling forward would skip
February entirely while a key was held.

## Accessibility

- **The month is announced when it changes**, once, in a polite live region.
  Everything under the header is replaced by a keystroke, and nothing about that
  moves for a reader who cannot see it.
- **Column headers carry the full weekday name** as text and the abbreviation for
  the eye. `abbr` alone leaves the header with no accessible text at all — axe
  says `empty-table-header`, and it is right.
- **A refused day is `aria-disabled`**, so it keeps its place in the grid and its
  place in the accessibility tree.
- **The cell is the control.** Each day is a focusable `<td role="gridcell">`
  with no button inside it, which is the shape the APG's own date grid uses. The
  focus, the accessible name and `aria-selected` are then on the same element —
  measured, a button inside the cell took the focus while the selected state
  stayed on the cell around it, so the node a user actually landed on carried no
  selection at all. `Enter` and `Space` choose the day, since a cell has no
  native activation of its own.
- **Forced colors**: the selected day keeps `Highlight`/`HighlightText`, the days
  outside the month and the refused ones keep `GrayText`. Those are the platform's
  own words for "chosen" and "not for you", and they are the only ones that
  survive when every background is flattened.
