# FormSegmentedControl

FormSegmentedControl is a bound set of one-of-many options, drawn as buttons — an alignment, a date range — already bound to the **form adapter in scope**. It renders `Fieldset` + `SegmentedControl`, and takes its control props and its error messages from the adapter, so the call site names no form library.

```tsx
<FormAdapterProvider adapter={useMyFormField}>
  <FormSegmentedControl name="align" label="Text alignment">
    <SegmentedControlItem value="left">Left</SegmentedControlItem>
    <SegmentedControlItem value="center">Center</SegmentedControlItem>
  </FormSegmentedControl>
</FormAdapterProvider>
```

## Props

`label` is the **legend** — the visible name of the set, and the only one it has. `SegmentedControl`'s own `label` is deliberately not passed through: two names are announced twice ("Text alignment, group … Text alignment, radio group"), and the visible legend is the one worth keeping ([ADR-0025](../../../../../apps/docusaurus/docs/adr/0025-one-of-many-is-a-radio-group.md)).

There is no `error` prop: the messages come from the adapter as a **list**, and register into the group's `aria-describedby` alongside the hint — announced once for the set rather than repeated on every option.

**What the binding owns is not a prop here at all** — `checked`, `onChange` and the value props are the library's, and passing one is a compile error rather than a field that silently stops reporting.

## Accessibility

Everything `SegmentedControl` guarantees — arrow keys that move and select, one tab stop, `form.reset()`, 44px under a coarse pointer — plus the wiring a bare group cannot do: the legend names the set, and the hint and messages reach it through `aria-describedby`.

A control with **no adapter in scope throws** rather than rendering: an unbound field picks perfectly well and submits nothing.

## Guidelines

### One field, many controls — what the binding has to be

A radio group is one field drawn as several controls, which the per-field binding could not express: it hands over one bag of native props, and here every radio needs the same `name` with a different `value` and a `checked` only the current value can answer.

So this component binds through **`optionField`**, not `field`. It asks the port once for the field and each segment then asks for its own props, which is what puts the binding's `name`, `checked`, `onChange`, `onBlur` **and its `ref`** on every radio.

**Your adapter needs an `optionField`.** Every binding in `@fmmenchi/ui-form-ports` ships one — `createRhfOptionField`, `createFormikOptionField`, `createTanstackOptionField`, `createConformOptionField`, `useActionOptionField` — and a hand-written adapter must add it, or this component throws and says so by name.

```tsx
<UiProvider
  adapters={{
    i18n,
    form: { field: useRhfField, optionField: useRhfOptionField, errors: useRhfErrors },
  }}
>
```

This is what an earlier version of this page called a limitation: the ref was not forwarded at all, so a library could not move focus here from an error summary and could not write a value back into the field. That is fixed, and the workaround this page used to recommend — composing `Fieldset` + `SegmentedControl` by hand — is no longer needed for the ref. It remains the answer for a per-field validation rule, which binding by name alone cannot carry.
