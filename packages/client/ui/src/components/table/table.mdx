# Table

Rows and columns, announced correctly.

```tsx
<Table
  caption="Persone"
  rows={people}
  getRowId={(p) => p.id}
  columns={[
    { key: 'name', header: 'Nome', rowHeader: true },
    { key: 'age', header: 'Età', align: 'end' },
  ]}
/>
```

## Anatomy

| part                                         | what it is                                              |
| -------------------------------------------- | ------------------------------------------------------- |
| `Table`                                      | the `<table>`, the caption, and the column model        |
| `TableHead` · `TableBody` · `TableFoot`      | the sections — and what makes `scope` derivable         |
| `TableRow` · `TableCell` · `TableHeaderCell` | the parts, for a layout the column model cannot express |

## Usage

<Canvas of={TableStories.Default} />

### We are not adding accessibility to a table. We are preventing its removal.

A `<table>` is already among the best-supported things in HTML: a screen reader announces its size on entry and, as the reader moves, the column header across and the row header down. All of that is free — and all of it depends on markup the average table gets wrong.

So `scope`, the accessible name and the empty row's `colSpan` are **not opt-in**. Behind a prop they would be missing from most tables, and the component would be delivering less than raw HTML already offered.

### The columns are data, and that is the whole design

It is not a style preference: it is the only way to **guarantee** the invariants that run across a row rather than watch for them.

- **Header and body cannot disagree.** Given markup, a caller can write four header cells and five body cells; every value is then attributed to the wrong column, and nothing on screen looks wrong.
- **`colSpan` is counted, not typed.** A hand-written number is wrong the day a column is added, and a short one leaves the empty message under one column instead of across the table.
- **A per-column decision is declared once.** In markup `align="end"` goes on the header _and_ on every row's cell — the same decision copied N times, which this package already forbids.

`rowHeader` deserves its own line: it renders `<th scope="row">` so a reader hears **which** row a cell belongs to. It is the thing nobody writes by hand, and declaring it on the column gives it to every row at once.

### The key is checked, and so is the value behind it

```tsx
{ key: 'name' }                               // ✓ a string property
{ key: 'nmae' }                               // ✗ compile error
{ key: 'placedAt' }                           // ✗ compile error — it is a Date
{ key: 'placedAt', cell: (o) => fmt(o.date) } // ✓ you said how
{ key: 'full', cell: (o) => `${o.a} ${o.b}` } // ✓ computed, so the key is free
```

Only **text and numbers** render on their own, nullable or not. A `Date`, an object, an array or a **boolean** must say how, and each for a measured reason: a `Date` or an object throws _"Objects are not valid as a React child"_ and takes the page down; an array renders `['a','b']` as `ab`, which looks deliberate; and a boolean renders **nothing at all**, so every `false` row shows a blank cell indistinguishable from missing data.

They are not formatted for you because there is no canonical rendering of `false` (a dash? "No"? an icon?) or of a date (which format, whose timezone?). Guessing would be a design system making a product decision.

**Two ergonomics notes the type does not tell you.** Annotate a hoisted column list — `const columns: Column<Person>[] = […]` — or TypeScript widens `key` to `string` and the error blames `cell`. And with a literal empty `rows={[]}` there is nothing to infer `T` from, so name it: `<Table<Person> rows={[]} …>`.

### Sorting, in three rungs

<Canvas of={TableStories.Sortable} />

**It works out of the box.** The hook takes the rows and gives them back ordered; the table shows which column and which way.

```tsx
const sort = useTableSort(people, { defaultSortKey: 'name' });

<Table
  rows={sort.rows}
  {...sort.props}
  columns={[{ key: 'name', header: 'Nome', sortable: true }]}
/>;
```

Free from that: "Àosta" before "Zurigo" — `<` puts every accented word after `z` — 9 before 10 rather than `"10"` before `"9"`, dates as dates, empty values at the bottom **in both directions**, `aria-sort` on the column in force and `none` on the ones offering, a real `Button` in the header, and every change announced in the reader's language.

**Sorting reads the row, not the cell.** The value compared is `row[key]`, never what `cell` rendered. For dates and money that is the right default — you sort by the `Date`, not by "14 Mar 2026" — and for a translated enum it is not: a `status` column displayed as "In attesa" orders by the invisible `PENDING`. Say so with a comparator when the display order is the one you mean.

**Override the column the default cannot know.** `priority` is not alphabetical, and no design system can guess that it runs low → medium → high. Write the ascending order only; the direction is applied for you.

```tsx
useTableSort(tickets, {
  compare: { priority: (a, b) => RANK[a.priority] - RANK[b.priority] },
});
```

Three things about `compare`, because none of them is visible from the type:

- **A computed column needs an entry here.** `{ key: 'fullName', cell: … }` has a key no row carries, so the engine finds `undefined` on every row, reads it as empty on both sides and reports every pair equal: the header turns, the change is announced, and nothing moves. It warns in development.
- **A typo is silent.** The key is a plain `string` — an index signature, so `prioriry` compiles, is never found, and the column falls through to alphabetical, which looks plausible enough to ship. Same warning catches it.
- **"Empty last in both directions" is the engine's, not yours.** Your comparator is negated whole for descending, so whatever it does with blanks reverses with everything else. Answer emptiness before you compare, if you care where it lands.

**Or take it over entirely.** When the server orders, use `useSortState` — the same hook without the engine, which then never enters your bundle — and put its state straight into the query key:

```tsx
const sort = useSortState({ defaultSortKey: 'name' });
const q = useQuery({ queryKey: ['people', sort.state], queryFn: fetchPeople });

<Table
  rows={q.data ?? []}
  busy={q.isFetching}
  {...sort.props}
  columns={columns}
/>;
```

The markup is identical in all three, and that is not a coincidence: **`Table` never sorts anything.** Reordering belongs to the hook or to the server; the component only ever displays the state. There is no "sorts twice" case because it does not sort once — which is also what dissolves the usual controlled/uncontrolled knot, since no prop here changes behaviour.

It does not compute the transition either. `onSortToggle` receives the **column key**, not the resulting state, so the cycle is applied by whoever owns the state and can read its latest value:

```tsx
<Table
  sort={sort}
  onSortToggle={(key) => setSort((prev) => nextSort(prev, key))}
/>
```

That is what `nextSort` is exported for, and the functional form is the point: computed from the `sort` prop instead, a consumer committing in `startTransition` gets a deferred value, and a second click recomputes from the first click's input — two clicks landing on ascending twice. It is also the seam for **a different cycle**: descending first for dates and scores, or two stops rather than three, is your own function in that same position.

The cycle we ship is **three stops, not two**: ascending, descending, and back to the order the data arrived in. A two-state toggle is more common and worse — once a reader has sorted a table there is no way back to the order the server chose, which in a ranking or a feed of events is the one that carries meaning.

**One state, one column.** `SortState` holds a single key; ordering by city and then by name is a `SortState[]`, and widening the type after consumers have put it in a query key is a breaking change — so it is deferred deliberately rather than half-available. Stability in `sortRows` does not give it to you: the hook always sorts the rows you hand it, not the ones it produced last time.

### It never sees where the rows came from

They arrive as an array, and an array does not say whether a `.sort()` or an `ORDER BY` produced it. The agnosticism is not discipline, it is an absence of information — which is what lets the same markup serve an in-memory list and a paginated server query.

`busy` follows from the same rule: it describes the **element's** state, not the data's provenance. A background refetch is busy while the old rows are still on screen, and so is a client-side re-sort. A `loading` prop would invite a spinner _instead_ of the data; this says "there is more coming" and keeps what is there.

### Not a grid

Cells here are content: they may **contain** controls, but nothing moves focus between them. `role="grid"` takes the arrow keys away from the assistive technology — which already has its own commands for moving through a table — and promises a full two-dimensional keyboard in return.

The practical test is **a matrix of inputs**: one column of inputs is still a table, because Tab's order (row by row) is the order you fill them in. A grid of them is not, and that is a different component with the whole APG keyboard or nothing.

Declaring the role and implementing half the keyboard is worse than not declaring it: it removes a mechanism that worked and substitutes one that does not.

### Composing instead

<Canvas of={TableStories.Composed} />

For a header group, a spanning row or a totals footer, drop to the parts. They are the substrate `Table` is built on, so this is decomposition rather than a second component — the relationship `Field` has to `FormInput`. The compiler keeps the two apart: `columns` and `children` cannot both be passed.

**What you give up, said plainly**, because it is the trade nobody documents: composing means the header/body agreement, the counted `colSpan` and the default empty state are yours to maintain. A header row composed outside a section also loses derived `scope` — it warns, and you pass `scope` yourself.

**Sorting does not come with you.** `sort` and `onSortToggle` are refused here rather than ignored: `aria-sort` needs a column list to land on, and accepting props that decide nothing is how a consumer spends an afternoon. Put the attribute on your own `TableHeaderCell` — it takes `aria-sort` like any `<th>` — and drive it with `useSortState`.

**What the column model cannot express yet**, so you know before you start: per-row attributes (a `className` or `data-*` on a `<tr>`) and column widths, which arrive with resizing. The first is the one most likely to push a consumer into composed mode, and it is worth telling us if it does.

## Accessibility

- **`scope` is derived from position**, not configured — and there are **three** positions, not two: a `<th>` in a header or footer section heads a column, one in the body heads a row, and one with no section around it gets **no `scope` at all**. That last case matters: with the attribute absent the browser's own header-assignment algorithm works it out correctly, so guessing there would overwrite a right answer with a wrong one. It warns in development instead.
- **A spanning header is a group**: `colSpan` on a header cell produces `scope="colgroup"`, so a two-level header's label reaches every column under it rather than only the first.
- **The caption is the accessible name**, and the warning fires whenever it renders no text — including `caption={cond && t('…')}` resolving to `false`, which is the shape a real call site writes. Wrap it in `VisuallyHidden` when the design has no room for it.
- **The empty row spans the table** so the message is laid out across it rather than under the first column. Note what that does _not_ do: a cell spanning every column is associated with **every** column header, so a reader hears them all before the message. It is a layout fix, not an association one.
- **The empty state has a default.** An empty `<tbody>` reads as "still loading" on screen and tells a screen reader nothing at all, so leaving `empty` out gives the design system's wording rather than silence.
- **`aria-sort` says two different things, and both are needed.** `ascending`/`descending` on the column in force describes the **data** — so a server-ordered column that has no control still says it is ordered — and `none` on the others marks them as **orderable**. The first version left `none` out, arguing the button already said so; it does not. The button's accessible name is the column heading, and the only other mark was a glyph carrying `aria-hidden`, so a reader had no way to learn the column could be sorted at all.
- **The sort trigger is a real `Button`**, so the focus ring, the touch target, keyboard activation and the forced-colors handling arrive with it rather than being re-derived. `NavGroup` hand-rolled one once and shipped with no focus ring at all.
- **All three stops are announced.** Reordering rows is invisible to anyone not looking, so a live region reports each change — including the **clear**, which used to render an empty string. Emptying a live region announces nothing: `role="status"` implies `aria-relevant="additions text"`, so a removal is not in the relevant set, and the stop this component argues hardest for was the one nobody was told about.
- **It is silent on arrival.** The region is rendered rather than pushed from an effect, and stays empty until the reader activates a header — so a table that mounts already sorted does not announce a sentence from nowhere.
- **A header that is not words needs `sortLabel`.** `header` is a `ReactNode`, so it may be an icon or an `<abbr>`; without a label the announcement falls back to the column's `key` and reads a developer identifier aloud, untranslated, inside localized copy. It warns.
- **The arrow is drawn inline**, not taken from the icon port. A table that could not show its sort direction until the app injected an icon set would be a table that breaks on somebody else's configuration. Its resting state is set by measurement rather than by eye: at the opacity first chosen it read 1.89:1 against the page, where WCAG 1.4.11 asks 3:1 of anything identifying a state.
- **Digits use `tabular-nums`** so a numeric column lines up, which is most of what makes one readable.
- **No vertical rules.** Lines between every column make a table read like a cage; alignment already groups a column for the eye.
- **The "one card per row" recipe on mobile is forbidden.** Changing `display` on table elements removes the role, and with it the reading mode. The role and that prohibition are one decision, not two.
- A very wide table stays hard even with perfect markup. The remedy there is content — fewer columns, a detail view, aggregates — not more attributes.
