# Table

Rows and columns, announced correctly.

```tsx
<Table
  caption="Persone"
  rows={people}
  getRowId={(p) => p.id}
  columns={[
    { key: 'name', header: 'Nome', rowHeader: true },
    { key: 'age', header: 'Età', align: 'end' },
  ]}
/>
```

## Anatomy

| part                                         | what it is                                                |

## Usage

<Canvas of={TableStories.Default} />

### We are not adding accessibility to a table. We are preventing its removal.

A `<table>` is already among the best-supported things in HTML: a screen reader announces its size on entry and, as the reader moves, the column header across and the row header down. All of that is free — and all of it depends on markup the average table gets wrong.

So `scope`, the accessible name and the empty row's `colSpan` are **not opt-in**. Behind a prop they would be missing from most tables, and the component would be delivering less than raw HTML already offered.

### The columns are data, and that is the whole design

It is not a style preference: it is the only way to **guarantee** the invariants that run across a row rather than watch for them.

- **Header and body cannot disagree.** Given markup, a caller can write four header cells and five body cells; every value is then attributed to the wrong column, and nothing on screen looks wrong.
- **`colSpan` is counted, not typed.** A hand-written number is wrong the day a column is added, and a short one leaves the empty message under one column instead of across the table.
- **A per-column decision is declared once.** In markup `align="end"` goes on the header _and_ on every row's cell — the same decision copied N times, which this package already forbids.

`rowHeader` deserves its own line: it renders `<th scope="row">` so a reader hears **which** row a cell belongs to. It is the thing nobody writes by hand, and declaring it on the column gives it to every row at once.

### The key is checked, and so is the value behind it

```tsx
{ key: 'name' }                               // ✓ a string property
{ key: 'nmae' }                               // ✗ compile error
{ key: 'placedAt' }                           // ✗ compile error — it is a Date
{ key: 'placedAt', cell: (o) => fmt(o.date) } // ✓ you said how
{ key: 'full', cell: (o) => `${o.a} ${o.b}` } // ✓ computed, so the key is free
```

Only **text and numbers** render on their own, nullable or not. A `Date`, an object, an array or a **boolean** must say how, and each for a measured reason: a `Date` or an object throws _"Objects are not valid as a React child"_ and takes the page down; an array renders `['a','b']` as `ab`, which looks deliberate; and a boolean renders **nothing at all**, so every `false` row shows a blank cell indistinguishable from missing data.

They are not formatted for you because there is no canonical rendering of `false` (a dash? "No"? an icon?) or of a date (which format, whose timezone?). Guessing would be a design system making a product decision.

**Two ergonomics notes the type does not tell you.** Annotate a hoisted column list — `const columns: Column<Person>[] = […]` — or TypeScript widens `key` to `string` and the error blames `cell`. And with a literal empty `rows={[]}` there is nothing to infer `T` from, so name it: `<Table<Person> rows={[]} …>`.

### Sorting, in three rungs

<Canvas of={TableStories.Sortable} />

**It works out of the box.** The hook takes the rows and gives them back ordered; the table shows which column and which way.

```tsx
const sort = useTableSort(people, { defaultSortKey: 'name' });

<Table
  rows={sort.rows}
  {...sort.props}
  columns={[{ key: 'name', header: 'Nome', sortable: true }]}
/>;
```

Free from that: "Àosta" before "Zurigo" — `<` puts every accented word after `z` — 9 before 10 rather than `"10"` before `"9"`, dates as dates, empty values at the bottom **in both directions**, `aria-sort` on the column in force and `none` on the ones offering, a real `Button` in the header, and every change announced in the reader's language.

**Sorting reads the row, not the cell.** The value compared is `row[key]`, never what `cell` rendered. For dates and money that is the right default — you sort by the `Date`, not by "14 Mar 2026" — and for a translated enum it is not: a `status` column displayed as "In attesa" orders by the invisible `PENDING`. Say so with a comparator when the display order is the one you mean.

**Override the column the default cannot know.** `priority` is not alphabetical, and no design system can guess that it runs low → medium → high. Write the ascending order only; the direction is applied for you.

```tsx
useTableSort(tickets, {
  compare: { priority: (a, b) => RANK[a.priority] - RANK[b.priority] },
});
```

Three things about `compare`, because none of them is visible from the type:

- **A computed column needs an entry here.** `{ key: 'fullName', cell: … }` has a key no row carries, so the engine finds `undefined` on every row, reads it as empty on both sides and reports every pair equal: the header turns, the change is announced, and nothing moves. It warns in development.
- **A typo is silent.** The key is a plain `string` — an index signature, so `prioriry` compiles, is never found, and the column falls through to alphabetical, which looks plausible enough to ship. Same warning catches it.
- **"Empty last in both directions" is the engine's, not yours.** Your comparator is negated whole for descending, so whatever it does with blanks reverses with everything else. Answer emptiness before you compare, if you care where it lands.

**Or take it over entirely.** When the server orders, use `useSortState` — the same hook without the engine, which then never enters your bundle — and put its state straight into the query key:

```tsx
const sort = useSortState({ defaultSortKey: 'name' });
const q = useQuery({ queryKey: ['people', sort.state], queryFn: fetchPeople });

<Table
  rows={q.data ?? []}
  busy={q.isFetching}
  {...sort.props}
  columns={columns}
/>;
```

The markup is identical in all three, and that is not a coincidence: **`Table` never sorts anything.** Reordering belongs to the hook or to the server; the component only ever displays the state. There is no "sorts twice" case because it does not sort once — which is also what dissolves the usual controlled/uncontrolled knot, since no prop here changes behaviour.

It does not compute the transition either. `onSortToggle` receives the **column key**, not the resulting state, so the cycle is applied by whoever owns the state and can read its latest value:

```tsx
<Table
  sort={sort}
  onSortToggle={(key, o) => setSort((prev) => nextSort(prev, key, o))}
/>
```

That is what `nextSort` is exported for, and the functional form is the point: computed from the `sort` prop instead, a consumer committing in `startTransition` gets a deferred value, and a second click recomputes from the first click's input — two clicks landing on ascending twice. It is also the seam for **a different cycle**: descending first for dates and scores, or two stops rather than three, is your own function in that same position.

The cycle we ship is **three stops, not two**: ascending, descending, and back to the order the data arrived in. A two-state toggle is more common and worse — once a reader has sorted a table there is no way back to the order the server chose, which in a ranking or a feed of events is the one that carries meaning.

**Stability does not give you a second column.** `sortRows` is stable, but the hook always sorts the rows you hand it rather than the ones it produced last time — so sorting by name and then re-sorting by city does not leave name as a tie-break. Say what you mean with a list; see [More than one column](#more-than-one-column).

### More than one column

Hold **Shift** while activating a header — with the pointer or with `Enter`/`Space` — and the column joins the order instead of replacing it. The first entry decides, the second breaks its ties, and so on.

```tsx
sort={[
  { key: 'city', direction: 'asc' },
  { key: 'age', direction: 'desc' },
]}
```

**`sort` is a list, always.** Filters have always been plural — several columns narrow the view at once — and sorting was the one axis that could hold a single opinion. The single case is a list of one; the alternative is two shapes and a normalisation at every read.

**One gesture, one path.** `Enter` on a button produces a click carrying the modifiers, so the component reads `event.shiftKey` once and the pointer and the keyboard cannot drift apart. What reaches you is the intent — `onSortToggle(key, { additive })` — and never the resulting state, the same bargain the key already made.

**`aria-sort` marks the leading column only.** ARIA asks for one at a time, and rightly: two headers both announced "sorted ascending" say nothing about which of them decided the order. The others carry no `aria-sort` at all rather than `none`, which ARIA defines as "no defined sort applied" — false for a tie-break.

What a reader needs instead is the rank, which the attribute cannot express, so every sorted header carries it in words ("sort 2 of 3") and only when there is more than one to rank. **The words go on the control when there is one**, because a header cell's name is re-announced with every data cell under it — measured once already for the filter trigger, and again here ("Età sort 2 of 2, 41" on two hundred rows). A column the server ordered has no control, so its cell carries the rank and pays that price; it is the only place the rank enters a header's name.

**The announcement is about the column you acted on** ("Sorted by Età, ascending, sort 2 of 2."), not about the leader. Describing the leader was the first design and it was silent for the commonest multi-column gesture there is: reversing a secondary changes neither the leader nor the count, so the sentence came out byte-identical — and a live region whose text does not change announces nothing at all.

**Hiding a sorted column is a hole worth knowing about.** The rows stay ordered by it, its header is gone, and nothing on screen can change or clear it; `showAll()` is the way out. The component warns in development, and the announcement says "Sorting changed." rather than claiming the sorting was removed.

**Shift is not discoverable, and that is the honest cost.** It is the convention every table library settled on, and a menu per column would charge two clicks to the case that only ever sorts by one. If your readers need to find it without being told, put the affordance in the toolbar where the other view controls live.

### Selecting rows

<Canvas of={TableStories.Selectable} />

```tsx
const selection = useRowSelection();

<Table
  rows={people}
  getRowId={(p) => p.id}
  columns={columns}
  {...selection.props}
/>;
```

**The hook is not given the rows.** It used to be, to work out what "select all" meant — which put the rendered rows in two places with nothing tying them together, and the paginated consumer paid for it: hook over the whole result set, table over a slice, and one click on a header box showing three rows selected six. `Table` reports which ids its header box spoke for, so there is one source of that fact, and `getRowId` is asked for once by the component that renders the rows.

**The checkbox column is ours to draw**, and that is not a convenience. The part that goes wrong is never the box, it is what the box is _called_: five controls all named "Select row" are five controls a screen reader cannot tell apart. Each one is named after its row — **"Select Zurigo"** — which is why a `rowHeader` column is required here, and why both leaving it out and rendering nothing in it warn.

**`aria-selected` is not used**, and the reason is worth stating precisely: it is a _supported_ property of the `row` role, but it is only meaningful inside a `grid` or `treegrid`. In a table it is not announced, so writing it would be an attribute that reads as a promise and delivers nothing. The checkbox _is_ the state for everyone, the row tint is decoration, and the box is not optional. In forced colors the tint is restated with the system's own selection colours — and so is the focus ring landing on it, which would otherwise be `Highlight` drawn on `Highlight`.

**The header box has three states**, and the mixed one is the reason it is our `Checkbox`: the DOM has no attribute for `indeterminate`, only a property, so a bare `<input>` with `checked={false}` says "none selected" when half of them are. Clicking a half-filled box **completes** it rather than emptying it, which is the convention everywhere and matches what mixed means.

#### Selection is a rule, not a list

This is the one place the model is not the obvious one, and paginated tables are why:

```tsx
{ mode: 'include', ids: new Set(['a', 'b']) }   // these two
{ mode: 'exclude', ids: new Set(['c']) }        // everything except this one
```

A reader who ticks "select all" on ten thousand rows has selected rows the browser has never received. There is no honest list to write — inventing one means fetching every page — but there is an honest **rule**, and it is one object with an empty set. It survives page changes, and the bulk action you send is "everything matching the filter except these three", which is what they actually asked for.

Three consequences worth knowing before you build on it:

- **The header box speaks only for the rows on screen.** It receives their ids, and nothing else. "Select all 10,000 matching" is a second affordance — the banner that appears after the header box is ticked — and only you know whether there are more rows. Build it with the exported `EVERYTHING_SELECTED`.
- **Unticking the header under an `exclude` rule clears the selection whole**, rather than narrowing it to "everything except the twenty you can see". Nobody means the second thing, and the first version did it: the box, the rows and the count all read zero while the rule still selected every row on the other 499 pages — a delete confirmed as "0 rows" that removes 9,997.
- **`count` is `undefined` under an `exclude` rule** unless you pass `total`, and that is an answer rather than a gap. `total` is the **result set's** size, never the page's: handing over `rows.length` turns "everything except three of ten thousand" into "seventeen", which is how a confirmation dialog says "delete 3 records" and deletes ten thousand.

#### The toolbar: what the view is showing, and what you can do to it

<Canvas of={TableStories.BulkActions} />

```tsx
const selection = useRowSelection({ total: data.total });

<TableToolbar {...selection.toolbarProps}>
  <ToolbarItem>
    <Button onClick={remove}>Elimina</Button>
  </ToolbarItem>
</TableToolbar>;
```

`Table`'s live region announces a change **once** and falls silent, which is right for an announcement and useless as a state: nothing answers "how many are selected?" a minute later, or after tabbing back. `TableToolbar` is that answer, on screen, for everybody — and deliberately **not** a live region itself, since two of them over one fact say it twice.

**It is one container, not one per feature.** It began as a selection bar and filters were about to arrive as a second one — two landmarks appearing and disappearing on unrelated schedules, which is two rotor entries coming and going for reasons a reader cannot correlate. Permanent, with contents that change, it is a stable destination: `summary` is the slot for what the view is showing, the selection composes itself, and `children` are your bulk actions. Given nothing to say and nothing to do it renders nothing at all.

It is also where `exclude` becomes reachable. Give the hook a `total` and, whenever fewer rows are selected than the query matched, the bar offers **"Select all 2,450"** — the escalation that produces "everything except these". Before it existed, a consumer had to assemble that from an exported constant, which is exactly the shape every review of this model called a trap.

The offer is keyed on `count < total`, not on the page being covered, and that is a deliberate narrowing of what the bar can know: it never learns how many rows the table rendered, and asking for that number a second time is precisely the duplication the hook was corrected to remove. It reads as a labelled button rather than as a leading question, so it is legible at any count.

Three things it does that a hand-rolled bar does not:

- **The actions are a `Toolbar`**, so six bulk actions cost one tab stop rather than six.
- **Focus comes back when the bar goes** — from our Clear button or from a bulk action of yours. A conditional bar unmounts the control that was just used, and focus falls to `<body>`: the classic way a keyboard user loses their place.
- **The count goes through `Intl`.** English groups four digits and Italian does not — `Select all 2,450` and `Seleziona tutte le 2450` — which is not something a template gets right.

**Wiring it yourself?** `Table` reports intents here exactly as it does for sorting, so the transitions are exported too — `toggleRow`, `toggleRows`, `coverageOf`, `isRowSelected`. Use them rather than reading `mode` in your own code: the two readings of `ids` are the one place this model bites, and `useRowSelection` also gives you `setSelection` for the changes that are not a single toggle, like a shift-click range.

**It is not a projection parameter.** Sorting and filtering derive the rows; selection is downstream of them and derives nothing, so it belongs in a request body rather than in a query key — which is also why it is a `Set` and not an array. Putting it in a query key is how ticking a box refetches the page.

### Declaring widths

<Canvas of={TableStories.DeclaredWidths} />

```tsx
columns={[
  { key: 'name', header: 'Nome', rowHeader: true },
  { key: 'city', header: 'Città', width: '10ch' },
  { key: 'age', header: 'Età', align: 'end', width: '6ch' },
]}
```

`width` takes any CSS length. **`ch` is usually the right unit for text** — it is the width of a "0", so `'10ch'` is about ten digits and stays right when the reader changes their font size, which a `rem` does not.

**Declaring one puts the table in `table-layout: fixed`**, and that is the point rather than a side effect: under the automatic algorithm a width is a _suggestion_ the browser overrides whenever the content is wider, so the declaration would sometimes do nothing and never say so — the class of defect this component spends its warnings on. Deriving the layout from the columns is also why there is no `layout` prop: a second fact that has to agree with the first is a second fact that can disagree with it.

What it costs, said rather than discovered: content no longer widens its column, so long text wraps and `white-space: nowrap` clips. Columns with no width share what is left, equally. And the width is the **outer** one — the cell's own padding is inside it, so `'10rem'` measures 10rem on screen rather than 10rem plus sixteen pixels you did not choose.

**This is the declarative half.** It covers the common case — "that column is three times wider than it needs to be" — decided once by whoever built the table. The other half, where the reader decides, is below.

### Resizing

```tsx
const widths = useColumnWidths();

<Table
  rows={people}
  getRowId={(p) => p.id}
  columns={columns}
  resizableColumns
  {...widths.props}
/>;
```

`resizableColumns` is a **table-level** switch and `Column.resizable` overrides it one column at a time — `false` to keep an identifier column legible, `true` where the table says nothing. One rule, `column.resizable ?? resizableColumns`, rather than two facts that can disagree. The **last column never gets a handle**: its trailing edge is the edge of the table, so dragging it would resize the table rather than a column.

`useColumnWidths` overrides `Column.width` key by key; a column with no entry keeps what it declared, which is why a reset **deletes** rather than storing the declared value back. Unlike the sort and the filters this is a **layout** parameter, not a projection one: it decides nothing about which rows exist, so it belongs in whatever remembers a reader's preferences and **not** in a query key — putting it there refetches the rows because somebody dragged a border.

**There is no persistence adapter here, and that is a decision rather than a gap.** Storage is where a design system stops being framework-agnostic: `localStorage` is wrong for an app that syncs preferences to a profile, a profile is wrong for one that does not have accounts, and both are wrong on a server render where neither exists. What the hook owes is a state shape that survives a round trip — a plain `Record<string, string>` of CSS lengths, no class instances, no functions, `JSON.stringify` and back — and it does. Wiring is four lines the consumer writes once:

```tsx
const [widths, setWidths] = useState(() =>
  JSON.parse(localStorage.getItem('people.widths') ?? '{}'),
);
const columns = useColumnWidths({
  widths,
  onWidthsChange: (next) => {
    setWidths(next);
    localStorage.setItem('people.widths', JSON.stringify(next));
  },
});
```

One thing to know before storing it: a stored width outlives the column it named. Rename a column's `key` and the old entry stays in the object forever, sizing nothing — harmless, but it is why the reset is a delete and why `resetWidths()` is worth putting behind a control somewhere.

#### Three ways to move a border, and why there are three

**There is no APG pattern for column resize.** The nearest is Window Splitter, which divides two panes; every accessible implementation in the wild is a `grid`, where the arrow keys belong to the component. This table is not a grid on purpose (ADR-0016), so the handle costs a **tab stop** — the price stated once rather than discovered.

- **Drag it.** What everyone expects, and what serves nobody else.
- **Arrow keys**, once it is focused: `←`/`→` by 16px, with `Shift` by 64, `Home` to the minimum, `End` to the widest the column may be, `Enter` back to the declared width. That widest is **not** the table's width: under `table-layout: fixed` a column given the whole table takes it, and the others render nothing — so the ceiling leaves every other column its own minimum. Every one of these keys is named in the handle's description, because `End` is the one that takes the most and `Enter` is the way back from it.
- **Press the handle, then press where the border goes.** WCAG **2.5.7 Dragging Movements** asks for a single-pointer path that is not a drag, and a keyboard does not satisfy it: the criterion exists for people who use a pointer and cannot hold a button down while moving it. So a press **latches** the handle, and the next press inside the table places the border there — WCAG's own example of a non-drag path. With a mouse the border also follows the pointer in the meantime, which is preview, not the mechanism: **a touch pointer only moves while it is touching, and touching is the drag**, so a version that resized on movement and used the second press only to stop was unmet for exactly the people the criterion is written for (measured on a real touchscreen). A press outside the table cancels, `Escape` cancels, and the mode is drawn and announced — a mode nobody is told about is a mode nobody knows they are in.

Double-clicking the handle restores the declared width, which is the gesture every table with draggable borders has taught people to expect.

**It reports one width per gesture, never one per pixel.** A width is what the browser recomputes sixty times a second, and routing that through React re-renders every row to move one border — so the handle writes the cell's inline size itself and reports the intent when the gesture ends. The same shape the filter's Apply has.

**A sticky header still sticks.** The handle needs a positioned cell to sit in, and `position: sticky` is already one — so the positioning is only declared for tables whose header is not sticky. Declared for both, it outspecified the sticky rule and turned it off silently, taking the opaque header, the scroll padding and the 2.4.11 protection with it.

**Two costs, said rather than discovered.** A resizable table is in `table-layout: fixed` from the start, before anything is dragged — under the automatic algorithm a width is a suggestion the browser overrides whenever the content is wider, so the first drag would move the border and the column would spring back. And the cells take a **wider inline padding**, because the 24px handle straddles each boundary and half of it has to stay clear of the heading and of the filter control. That is the compactness bargain: the boundary earns its own region, and the sort and the filter keep theirs.

A column declared in `%` or `vw` warns: the gesture measures the rendered column and reports pixels, so the first drag replaces the relative width with a fixed one. `Enter` puts it back.

For a layout the column model cannot express, `TableColumnResizer` is exported on its own — it takes `label`, `onResize` and `onReset`, and reads the cell it sits in.

### Marking a row

`getRowProps` puts a `className` or a `data-*` on the row a datum produced — the cancelled one struck through, the overdrawn one tinted, a `data-testid` for a test to find.

```tsx
getRowProps={(invoice) => ({
  className: invoice.status === 'void' ? styles.void : undefined,
  'data-overdue': invoice.dueAt < today ? '' : undefined,
})}
```

**It takes no handlers, and that is the same refusal as [Not a grid](#not-a-grid).** A `<tr>` is not focusable, so an `onClick` here is a control no keyboard can reach. A row that acts puts a link or a button in a cell, where the platform announces it and Tab arrives at it. It also takes no `id` and no `hidden`: those tie a detail row to the button that controls it, and `hidden` takes the row out of the accessibility tree while its checkbox stays focusable.

**The refusal is a runtime one, not a type one**, and it is worth knowing which. `TableRowAttributes` rejects an extra key only under a direct annotation — an object literal loses excess-property checking in a function's return position, which is the one position this prop is ever written in. So anything else you return is **dropped**, with a development warning naming it.

What the component sets wins: a `data-selected` returned from here is overwritten rather than honoured, because the checkbox and the attribute have to agree and only one of them can be the source. And these attributes reach the row the datum produced, never the detail row beside it.

### Expandable rows

```tsx
const rows = useRowExpansion();

<Table
  rows={people}
  getRowId={(p) => p.id}
  columns={columns}
  renderDetail={(person) => <PersonSummary person={person} />}
  {...rows.props}
/>;
```

**This is the first thing the column model cannot express**, and `renderDetail` is the escape hatch rather than a hole: a detail is prose, a form, a nested list, a chart — none of which a `Column` describes. Given nothing to render the control is not drawn at all, because a chevron that opens an empty row reads as missing data rather than as an unwired feature.

**The state is on the button, and that is forced.** `aria-expanded` is listed as supported on `row` — but only inside a `grid` or `treegrid`; on a row in a `table` it is not announced, so writing it there would be an attribute that reads as a promise and delivers nothing. It is the same trap `aria-selected` sets one feature over, and the same answer: the control carries the state, for everybody.

**The detail row is rendered while it is shut**, and merely `hidden`. That is what keeps `aria-controls` honest — a reference to an element that is not in the document is a promise to nobody — and `hidden` takes the row out of the accessibility tree and out of the tab order, which a class cannot. What is _inside_ it is built only when it is open, because `renderDetail` is a function and calling it for every shut row of a long table is work nobody asked for.

Two costs, stated:

- **A spanning cell is joined to every column header.** A cell across the whole table is associated with all of them, so a reader hears every heading before the detail. It is named — "Details for Milano" — which is the one thing that makes that bearable, and it is why the row header matters here as much as it does for the checkboxes.
- **A detail row is a row.** A screen reader counts it, and "row 4 of 7" becomes "row 4 of 13" on a table with six open panels. Nothing can fix that inside a `<table>`; a `treegrid` could, and it is a different component.

### Filtering

```tsx
const filters = useTableFilters(people, { defaultFilters: { city: 'Milano' } });

<TableToolbar
  {...filters.toolbarProps}
  filterLabels={{ city: 'Città' }}
  total={people.length}
/>
<Table
  rows={filters.rows}
  getRowId={(p) => p.id}
  columns={[
    { key: 'name', header: 'Nome', rowHeader: true },
    { key: 'city', header: 'Città', filterable: true },
  ]}
  {...filters.props}
/>;
```

**Filters are a projection parameter**, like the sort and unlike the selection: they decide which rows _exist_, so they belong in a query key and in a URL — a reader who filtered and reloaded expects the same twelve rows. That is why the state is a plain `Record<string, string>` and why there are two hooks: `useFilterState` holds it, `useTableFilters` is that plus the matching, so a consumer whose server filters never pulls the matcher into their bundle.

**The matcher is not `includes`.** Every app that writes its own filter writes `String(cell).includes(query)`, and that comparison says "Àosta" does not contain "aosta"; in Turkish it says "İzmir" does not contain "izmir", because the dotted capital lowercases to an `i` followed by a combining dot. The fold is case first **in the reader's language**, then ß→ss, then the Greek final sigma, then `NFKD` and the marks — which also folds the ligature `ﬀ` and full-width `ＡＢＣ`.

Two things it deliberately does **not** do:

- **It keeps the Japanese voiced marks.** They are `Diacritic=Yes` and `NFKD` splits them off, so stripping the class blindly folds バス (bus) to ハス (lotus). Those are different words, and a filter that conflates them is a false-positive engine rather than a forgiving one.
- **It honours Turkish casing**, so under `tr` a capital `I` folds to the dotless `ı` and "Istanbul" does not match "istanbul". Correct for Turkish words, surprising for loanwords, and the price of folding in the reader's language rather than the runtime's.

**Apply, do not filter as you type.** `onFilterApply` is the moment a draft becomes the view. Filtering on every keystroke deletes rows under a reader continuously — the silent change sorting had, at a higher rate — and gives the live region nothing discrete to announce. The toolbar announces the new row count when it changes, because `Table`'s own region only exists when sorting or selection is wired and filtering happens outside the component.

#### The control in the header

`filterable` puts a **trigger** in the column's header — a small control that opens an editor — rather than an input sitting under the heading. The difference is what it costs when nobody is filtering: a permanent box is a tab stop on _every_ filterable column, always, plus a row of chrome above the data; the trigger is one stop, and what it opens exists for as long as the reader is editing. Compactness is a goal here, not a preference: a table is dense by definition and every row of chrome pushes the data further down.

**Discriminated by region, not by menu.** Sorting is the heading; filtering is the control beside it; resizing (when it lands) is the boundary between two columns. Three distinct areas, three distinct affordances — which is why there is no single "column menu" absorbing all of them. The cost is stated: a column that both sorts and filters is **two tab stops**, and that is the price of a `<table>` rather than a `grid`, where the arrow keys would be ours to spend.

**The state is in the name.** Applied, the trigger is called "Filter Città, currently Milano". The funnel — `FilterGlyph`, drawn here rather than borrowed, because an icon set is brand identity and lives app-side — is the second channel and not the only one, and the value drawn beside it is `aria-hidden` and free to truncate — a state carried by colour alone reaches nobody who cannot see it, and hearing the value twice is its own defect.

**Every way out that is not Apply discards.** `Escape`, a click outside, closing — all of them leave the applied value alone, and the draft is reseeded from it on the next visit, so nothing abandoned waits around to be applied by a later Enter. Clearing is an **apply of nothing** rather than a second mode: same callback, same announcement, and the key leaves the state rather than sitting there empty, because `{ city: '' }` and `{}` are two cache entries for one view.

**The column's words live in two places, and that is the toolbar's price.** `Column.label` names the trigger and the header cell; `TableToolbar.filterLabels` names the same column in the summary, because the toolbar never sees the column model — which is what lets it work above a table it knows nothing about. Pass both, or the summary prints the key.

For a layout the column model cannot express, `TableFilterTrigger` is exported on its own and takes `label`, `value` and `onApply` — drive it with `useFilterState` from your own `TableHeaderCell`.

**Give the toolbar `filterLabels`.** The summary names the columns in force, and without a label it prints the key: `Filtrato per: created_at`, a developer identifier inside localized copy. It warns. Values are deliberately not shown — a value is whatever was typed, it belongs beside its own control where it is editable, and as a sentence it grows without bound.

**A column whose value does not mean "contains" says so**, with a predicate per key — a number that means "at least", a date that means "since". A key matching neither a predicate nor a row property warns, because otherwise it empties the table and blames a column nobody can see.

**While a filter is on, the "select all matching" offer is withheld.** It means everything the query matched, `total` is the unfiltered size, and the two cannot be reconciled from inside the toolbar — so the offer would have taken the rows the reader had just filtered away.

### Choosing which columns to show

`useColumnVisibility` holds which columns the reader has put away; `TableColumnsMenu` draws the list. `Table` learns nothing about either — it is handed fewer columns and draws fewer columns, the same silence it keeps about where the rows came from.

<Canvas of={TableStories.ColumnVisibility} />

```tsx
const visibility = useColumnVisibility({ columns });

<TableToolbar label="Vista">
  <ToolbarItem>
    <TableColumnsMenu {...visibility.menuProps} />
  </ToolbarItem>
</TableToolbar>
<Table columns={visibility.columns} rows={rows} getRowId={(r) => r.id} caption="…" />
```

**It belongs to the toolbar, not to a header cell.** A header cell's controls decide things about THAT column — how it sorts, what it filters by. Which columns exist is a decision about the whole view, and a control for it tucked inside one column's menu is a control nobody finds.

**It is a layout parameter, like the widths and unlike the sort.** Sorting and filtering decide which rows exist, so they belong in a query key and in a URL; this decides nothing about the data. Put it wherever a reader's preferences live — a query key would refetch every row because somebody unticked a column.

**Two columns refuse to go, and the menu says which reason applies.** The row header names each row: hide it and a screen reader announces every cell as "column 3, 47", while the table still renders and nothing on screen says anything went wrong. And the last one standing refuses too, because a caption over an empty grid reads as broken rather than chosen. Both are `aria-disabled` rather than `disabled` — inert, still reachable, still able to say what they are — and the reason is in the accessible name, because a disabled control whose reason is not announced is a dead end with no explanation.

**The count is in the trigger's name** ("Columns, 2 of 4 shown"), so the state is legible before the menu is opened and does not depend on seeing a glyph. And the menu stays open while you work: putting three columns away is three decisions, not three visits.

### Putting the columns in order

`useColumnOrder` holds the order and `TableColumnsMenu` draws it — the same menu that decides which columns are shown, because which columns and in what order are the same kind of decision about the view.

<Canvas of={TableStories.ColumnOrder} />

```tsx
const order = useColumnOrder({ columns });
const visibility = useColumnVisibility({ columns: order.columns });

<TableColumnsMenu {...visibility.menuProps} {...order.menuProps} />
<Table columns={visibility.columns} … />
```

The two hooks compose and neither learns about the other: order hands its columns to visibility, visibility hands what is left to the table.

**Alt with the arrow keys moves a column.** Plain arrows still walk the menu — the modifier is the whole distinction between reading the list and rearranging the view. The gesture is announced **once, on the menu**, and each entry says where it sits ("Città, 2 of 4"), because a screen reader announces one item and not the sequence around it. A locked column still says its position: it cannot be hidden, but it can be moved.

**Moves are clamped, not wrapped.** A column already first, asked to go earlier, stays — wrapping would send it to the end, which is a different thing from what the reader asked and, on a held key, an endless ride. A refused move still swallows the key, so the focus stays on the column being held rather than wandering off down the menu.

**The state is keys, not columns**, so it survives a trip through storage — a `cell` function does not. A stored order that has outlived the column list drops what has gone and puts anything new where it was **declared**, not at the end: a column added between two others belongs there, and appending would put it after the ones its author meant it to precede.

**Dragging is not here yet**, deliberately. The keyboard path is the prerequisite, not the consolation: drag will be a second way to call the same `move`, and building it first would have meant two sources for one order and discovering late that they disagree.

### A header that stays

<Canvas of={TableStories.StickyHeader} />

```tsx
<div style={{ blockSize: '16rem' }}>
  <Table
    caption="Persone"
    rows={rows}
    getRowId={(p) => p.id}
    columns={columns}
    stickyHeader
  />
</div>
```

**It brings its own scroller**, and that is the feature rather than a side effect. `position: sticky` with nothing scrolling around it pins to the **viewport** — so the header of a table halfway down a page rides over everything above it. The two are one thing, which is why one prop turns on both.

**The scroller is where the obligation lives.** A region that scrolls has to be reachable by keyboard: somebody who cannot use a pointer has no other way to reach the rows below the fold, or the columns off to the right. So it takes a tab stop — and a tab stop with no name is an entry a screen reader announces as nothing, so it borrows the `<caption>`, which is already the table's name and cannot drift from it.

**How tall it is belongs to you.** Constrain the box you put it in; given no constraint it does not scroll vertically and the header is a no-op rather than a bug.

**Its height is yours, and it has to be definite** — `block-size: 20rem`, or a flex or grid track. A `max-block-size` on the parent does not work: the container's own percentage resolves to `none` against an indefinite box, so nothing scrolls, the header never sticks, and the table overflows the box you just constrained. `scrollProps` is the other way in, and the one to reach for when you also want a `ref` or a class on the box that is actually laid out — `className`, `style` and `ref` go to the `<table>`, which stops being the outermost node the moment a wrapper appears.

Given no constraint at all, the whole thing is inert: nothing scrolls, and the container withholds its tab stop and its landmark rather than shipping dead ones.

Two things it does not do. The `<tfoot>` does not stick — a totals footer scrolls away, and if you need one pinned it is composed markup and CSS of your own. And the container is an `overflow: auto` box, so anything absolutely positioned inside a cell is clipped by it; this package's own surfaces are safe, because `Popover`, `Menu`, `Dialog` and `Toast` all render in the top layer, but a hand-rolled dropdown in a cell is not.

### It never sees where the rows came from

They arrive as an array, and an array does not say whether a `.sort()` or an `ORDER BY` produced it. The agnosticism is not discipline, it is an absence of information — which is what lets the same markup serve an in-memory list and a paginated server query.

`busy` follows from the same rule: it describes the **element's** state, not the data's provenance. A background refetch is busy while the old rows are still on screen, and so is a client-side re-sort. A `loading` prop would invite a spinner _instead_ of the data; this says "there is more coming" and keeps what is there.

<Canvas of={TableStories.Empty} />

### Not a grid

Cells here are content: they may **contain** controls, but nothing moves focus between them. `role="grid"` takes the arrow keys away from the assistive technology — which already has its own commands for moving through a table — and promises a full two-dimensional keyboard in return.

The practical test is **a matrix of inputs**: one column of inputs is still a table, because Tab's order (row by row) is the order you fill them in. A grid of them is not, and that is a different component with the whole APG keyboard or nothing.

Declaring the role and implementing half the keyboard is worse than not declaring it: it removes a mechanism that worked and substitutes one that does not.

### Composing instead

<Canvas of={TableStories.Composed} />

For a header group, a spanning row or a totals footer, drop to the parts. They are the substrate `Table` is built on, so this is decomposition rather than a second component — the relationship `Field` has to `FormInput`. The compiler keeps the two apart: `columns` and `children` cannot both be passed.

**The border model changed under every table, and this is where it bites.** It is now `separate` with no spacing: in the collapsed model a cell's borders belong to the **table** rather than to the cell, so a sticky header scrolls away from its own rule and arrives with no line under it. Nothing this component renders looks different — measured, cell geometry identical and one sub-pixel blend on one scanline. But the separated model **ignores a border set on a `<tr>`**, silently, so `<TableRow style={{ borderBottom: … }}>` written before this stopped drawing anything. Put it on the cells.

**What you give up, said plainly**, because it is the trade nobody documents: composing means the header/body agreement, the counted `colSpan` and the default empty state are yours to maintain. A header row composed outside a section also loses derived `scope` — it warns, and you pass `scope` yourself.

**Neither sorting nor selection comes with you.** `sort`, `onSortToggle`, `selection` and the selection toggles are refused here rather than ignored: `aria-sort` needs a column list to land on, and accepting props that decide nothing is how a consumer spends an afternoon. Put the attribute on your own `TableHeaderCell` — it takes `aria-sort` like any `<th>` — and drive it with `useSortState`. Selection is the same trade with a sharper edge: both hooks still work here, and `useRowSelection` hands you `coverage` for the header box's three states — but the per-row labelling, which is the part that actually goes wrong, becomes yours.

**What the column model cannot express yet**, so you know before you start: nothing on this list any more. Column widths arrived with resizing, and per-row attributes — the one that was most likely to push a consumer into composed mode — arrived as `getRowProps`.

## i18n

Four catalogs, because they say different things about different facts. Override a label through the `messages` port with `"<namespace>.<key>"`.

| namespace            | keys                                                                                                                                                                                    |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `table`              | `empty` · `sortedAscending` · `sortedDescending` · `sortCleared` · `select` · `selectRow` · `selectRowNamed` · `selectAllRows` · `selectionCount` · `selectionAll` · `selectionCleared` |
| `tableToolbar`       | `region` · `actions` · `count` · `all` · `allExcept` · `selectAllMatching` · `clear` · `filtered` · `filteredCount` · `unfiltered` · `unfilteredCount` · `filteredBy` · `clearFilters`  |
| `tableFilterTrigger` | `name` · `activeName` · `heading` · `apply` · `clear`                                                                                                                                   |

`table` announces what a click just did to the rows on **this page**; `tableToolbar` states what the rule and the filters cover, including rows nobody here has seen; `tableFilterTrigger` names one column's control and nothing else. What the trigger shares with the toolbar is the fact, not the sentence. They were one catalog briefly and it did not survive being checked — the shared keys rendered differently in the same instant while counting different things.

**The `tableToolbar` namespace was `tableSelectionBar`.** An app overriding the old keys is overriding nothing.

## Accessibility

- **`scope` is derived from position**, not configured — and there are **three** positions, not two: a `<th>` in the header section heads a column, one in the body or the footer heads a **row** — a totals label describes the values beside it, and `scope` can only point at subsequent cells, of which a footer has none below — and one with no section around it gets **no `scope` at all**. That last case matters: with the attribute absent the browser's own header-assignment algorithm works it out correctly, so guessing there would overwrite a right answer with a wrong one. It warns in development instead.
- **A spanning header is a group**: `colSpan` on a header cell produces `scope="colgroup"`, so a two-level header's label reaches every column under it rather than only the first.
- **The caption is the accessible name**, and the warning fires whenever it renders no text — including `caption={cond && t('…')}` resolving to `false`, which is the shape a real call site writes. Wrap it in `VisuallyHidden` when the design has no room for it.
- **The empty row spans the table** so the message is laid out across it rather than under the first column. Note what that does _not_ do: a cell spanning every column is associated with **every** column header, so a reader hears them all before the message. It is a layout fix, not an association one.
- **The empty state has a default.** An empty `<tbody>` reads as "still loading" on screen and tells a screen reader nothing at all, so leaving `empty` out gives the design system's wording rather than silence.
- **`aria-sort` says two different things, and both are needed.** `ascending`/`descending` on the column in force describes the **data** — so a server-ordered column that has no control still says it is ordered — and `none` on the others marks them as **orderable**. The first version left `none` out, arguing the button already said so; it does not. The button's accessible name is the column heading, and the only other mark was a glyph carrying `aria-hidden`, so a reader had no way to learn the column could be sorted at all.
- **The sort trigger is a real `Button`**, so the focus ring, the touch target, keyboard activation and the forced-colors handling arrive with it rather than being re-derived. `NavGroup` hand-rolled one once and shipped with no focus ring at all.
- **All three stops are announced.** Reordering rows is invisible to anyone not looking, so a live region reports each change — including the **clear**, which used to render an empty string. Emptying a live region announces nothing: `role="status"` implies `aria-relevant="additions text"`, so a removal is not in the relevant set, and the stop this component argues hardest for was the one nobody was told about.
- **It is silent on arrival.** The region is rendered rather than pushed from an effect, and stays empty until the reader activates a header — so a table that mounts already sorted does not announce a sentence from nowhere.
- **A header that is not words needs `label`.** `header` is a `ReactNode`, so it may be an icon or an `<abbr>`; without a label the announcement falls back to the column's `key` and reads a developer identifier aloud, untranslated, inside localized copy. It warns.
- **Every selection checkbox says which row it selects**, by pointing `aria-labelledby` at the row's own header cell rather than stringifying it — so an icon or an `<abbr>` in that cell still reads correctly. Without a `rowHeader` column there is no noun to point at, and the honest fallback ("Select row", identical on every row) warns rather than pretending a row number means something after a re-sort.
- **A selected row is announced by its checkbox and nothing else**, because `aria-selected` is only meaningful inside a `grid` or `treegrid` and is not announced on a row in a table. Only the header box announces a count, and only because it changes many rows at once — repeating one over every individual tick doubles what the checkbox already says. Its sentence is captured when you click it, not derived from the current rows: derived, it re-announced on the next row tick and on a refetch that returned one row fewer, with nobody having touched anything.
- **The verb lives outside the table.** A row whose name is an element rather than a string — a link, an icon, an `<abbr>` — has no string to put in a message, so its checkbox is labelled by a hidden "Select" plus the row's own header cell. That span used to sit in the header cell, which is where a `columnheader` takes its name from, so the column announced itself as "Select Select all rows" and every cell in it carried the extra word.
- **The toolbar is a named region with a STABLE name** — "Table controls" — and its summary is its description. The name used to be the count, which answered "how many?" through the landmark and was right for a bar that existed only while a selection did; permanent, a name that changed with the view would rename the landmark under the reader. Both the region and its `Toolbar` are `aria-describedby` the summary, so entering the landmark and tabbing straight into the actions both state it.
- **Render the toolbar ABOVE the table**, and that is a reversal of what the selection bar shipped with. A bar that _appeared_ when you selected had to come after, because forward Tab never reached actions that materialised behind the reader. A permanent one is not a surprise: it is there before you act, it is a named landmark — one jump with a screen reader, a few Shift+Tabs otherwise — and the filters that share it **describe what you are about to read**, which is worthless after the rows. The residual cost is real and stated: acting on a selection means going back up.
- **Focus comes back when the bar goes**, by whatever route: our Clear button, or a bulk action of yours that empties the selection. The element focused when the bar appeared is restored, which scrolls the page back to it — a focus you cannot see is not a focus. A bar that mounts already visible has no origin to return to, and says so by doing nothing.
- **A sticky header takes a tab stop with it — but only when there is something to scroll.** The container is focusable and named by the `<caption>`, because a region that scrolls and cannot be focused is unreachable to anyone without a pointer; when nothing scrolls it withholds both, since a tab stop over content that does not move is a stop for nothing. The header itself is painted opaque, or the rows scroll straight through it.
- **A focused control is never scrolled under the header.** Moving BACKWARD through a table — Shift+Tab up through the rows, the ordinary way to review a list — makes the browser scroll the target to the top of the scrollport, which is exactly where the header is: measured at 36px of a focused checkbox buried, against 18px of checkbox. The container is told how tall its own header is, so it stops there instead. Chromium already handles the programmatic `.focus()` case; sequential navigation is the one that needed it (WCAG 2.4.11).
- **The arrow is drawn inline**, not taken from the icon port. A table that could not show its sort direction until the app injected an icon set would be a table that breaks on somebody else's configuration. Its resting state is set by measurement rather than by eye: at the opacity first chosen it read 1.89:1 against the page, where WCAG 1.4.11 asks 3:1 of anything identifying a state.
- **A resize handle is operable three ways, and the third one is the criterion.** WCAG **2.5.7 Dragging Movements** asks that anything done by dragging be reachable by a single pointer without a drag, and a keyboard does not satisfy it — the criterion is written for people who use a pointer and cannot hold a button while moving it. A press latches the handle and the next press inside the table **places** the border, which is a gesture a finger can make: a version that moved the border on pointer movement was unmet on touch, where a pointer only moves while it is touching. `Escape` puts the column back, and the latched state is drawn AND announced.
- **The handle is a focusable `separator`** carrying `aria-valuenow`/`min`/`max` — the Window Splitter pattern, which is the nearest ARIA has: there is **no APG pattern for column resize**, and every accessible implementation in the wild is a `grid`, where the arrow keys belong to the component. In a `<table>` they do not, so the handle costs a tab stop per resizable column. That is the price of not being a grid, and it is paid rather than hidden.
- **Its 24px target is bought with padding, not with a thick line.** The grip straddles the boundary, so half of it lies in each neighbouring cell's inline padding — dead space on both sides — and a resizable table widens that padding to make room. The line the reader sees is 2px of it; the rest is target (WCAG 2.5.8).
- **A control in a header cell is named by the cell.** A `columnheader` takes its name from its contents and computes one for every descendant, so a filter trigger called "Filter Regione, currently Lombardia" or a handle called "Resize Regione" became part of the column's name and was read before every cell under it. Cells holding such a control carry an explicit `aria-label` instead — measured against Chromium's AX tree, since `dom-accessibility-api`, which this suite's matchers and axe use, does not reproduce the defect at all.
- **Digits use `tabular-nums`** so a numeric column lines up, which is most of what makes one readable.
- **No vertical rules.** Lines between every column make a table read like a cage; alignment already groups a column for the eye.
- **The "one card per row" recipe on mobile is forbidden.** Changing `display` on table elements removes the role, and with it the reading mode. The role and that prohibition are one decision, not two.
- A very wide table stays hard even with perfect markup. The remedy is content — fewer columns, a detail view, aggregates. `stickyHeader`'s container will scroll it horizontally with the keyboard access that requires, but that is a consequence of the header, not an answer to width: a table that is wide and short has no way to ask for the container on its own, and that gap is open on purpose until someone needs it.
