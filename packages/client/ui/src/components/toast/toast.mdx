# Toast

A message that arrives on its own and leaves on its own.

```tsx
<ToastRegion>
  <App />
</ToastRegion>;

// anywhere inside it
const { toast } = useToast() ?? {};
toast?.({
  variant: 'success',
  title: 'Saved',
  children: 'Your changes are live.',
});
```

## Anatomy

| part          | what it is                                                     |
| ------------- | -------------------------------------------------------------- |
| `ToastRegion` | the queue, and the live region the messages are announced in   |
| `useToast`    | `toast()` to raise one, `dismiss()` to take it back            |
| `Toast`       | one message — an `Alert`. A part: not exported, not used alone |

## Usage

### It goes inside the design system's provider, not around it

`ToastRegion` names itself and its dismiss control from the message catalogue, so it has to sit **inside** `UiProvider`:

```tsx
<UiProvider adapters={{ i18n }}>
  <ToastRegion>
    <App />
  </ToastRegion>
</UiProvider>
```

The other order breaks nothing loudly — the region still works, still announces, and simply calls itself "Notifications" in an app that is not in English. That is the worst way to find a bug, so it warns in development instead.

They are two providers on purpose. `UiProvider` renders an element only when it has something to carry, and folding a fixed, top-layer region into it would put one on every page of every consumer, including the ones that never raise a message. It would also turn a provider of _contracts_ into a provider that paints.

Mounting it once at the root is the intended shape, and costs what you would hope: only components that call `useToast()` re-render when the queue changes — measured — because `children` is the same element across renders and React bails out of the subtree. The pause on hover does not re-render anything outside the region.

### The queue lives in a provider, not in a module

The shorter API — an imported `toast()` backed by a module-level store — reads better at the call site and is **one object per process**. On a server that process serves every request, so two people would share a queue: one user's "Saved" appearing over another's page. Libraries that ship the imported form are client-only by construction; this package cannot assume that about its consumer, so the state goes where React already scopes state.

### The region is rendered empty, and stays

A live region and its first message appearing together is the classic way to announce nothing: assistive technology has to be watching a region that **already exists** to notice an insertion into it. So `ToastRegion` renders whether or not anything is up, and the toasts are inserted into it.

For the same reason each `Toast` passes `live="off"` to the `Alert` it is made of. An Alert announces itself by carrying its own live region — right when it is on the page from the start, wrong here, where it would be a second region around one message.

It is `role="status"`, not `alert`: a toast is not an interruption. An error still gets there, and `Alert`'s visually-hidden severity word says which it is, but it says so at the next pause — which is what a message the reader did not ask for deserves.

### Nothing races you to a control

The first version of this component gave every toast a ✕ and argued that nothing in it could be unreachable by keyboard, because it held no actions. That was circular, and a review said so: **the ✕ is the action**. The region renders after the whole app, so its controls are the last focusable things in the document — six seconds is not enough to Tab past thirty fields, and a screen reader in browse mode never gets there at all.

So the two cases are split, and the rule is one line:

- **a toast that stays has a ✕** — nothing is racing you to it;
- **a toast with a `duration` has none** — there is no control to reach.

### Staying is the default, and a `duration` is a promise

Auto-dismissal is a **WCAG 2.2.1 time limit**, and pausing on hover does not satisfy that criterion: it asks for the limit to be turned off, adjusted to ten times, or extended after a warning. A toast can offer none of those, and on a touch screen there is no hover to rest in at all.

What makes a timed message acceptable is that its content is **redundant** — available somewhere the reader can go back to. So the default imposes no limit, and passing a `duration` is a caller saying the message is not the only copy of itself.

The pause on hover remains, because reading is not the same as dismissing, and it is on the **region**: a pointer resting on one message must not let the one beneath it vanish from under the cursor. It **restarts** the clock rather than resuming it — a reader who arrives with 200ms left should not be handed 200ms.

### A neutral panel with a status edge

`Alert`'s tinted-surface treatment — a `*-subtle` fill across the whole box — is right for a message that is **part of** the page: one block among others, and the tint says which kind. A toast is not part of the page. It arrives over whatever the reader was looking at, unasked, and a panel of solid red or green there is a shout where a word would do.

So the fill is the page's own `card` colour and the status becomes an **edge**, using the same `--alert-border` the variant already set. Nothing new is mapped, and `card × card-foreground` is a pairing the token contract already declares.

### A timed toast shows how long is left

The bar runs on the **same custom property the timer uses**, so the thing on screen and the thing counting cannot promise different moments. It pauses with the clock — an indicator still draining while the timer is stopped would be a lie told sixty times a second — and it is `aria-hidden`, because it duplicates a fact a screen-reader user has by other means and a live region inside a live region announces nothing well. Under reduced motion it is not drawn at all: a continuously draining bar is exactly the movement the preference asks to be spared, and the message leaves either way.

A toast that **stays** has no bar, for the same reason it has a ✕ and a timed one does not: there is nothing to count.

### It arrives and it leaves

Both movements come from the shared keyframes in `@fmmenchi/tokens/styles/motion.css` — `fm-slide-up-in` is documented there as the toast shape, and this component had redeclared it locally, which is the drift the doctrine exists to prevent. Duration by **surface size** (`s`), ease by **direction**.

The exit goes through `animateExit`, the package's one piece of animation JavaScript, and is **awaited before the state changes** — without that React unmounts the node out from under the animation and the message blinks out. The doctrine's caveat that "only the Dialog can have an exit" is about intercepting a platform close event that is not cancelable elsewhere; nothing is intercepted here, because the removal is this component's own state and the delay is ours to take.

`fade`, not `scale`: a message that shrinks reads as being undone.

### It stacks newest first, and keeps five

DOM order is the visual order, so Tab follows the eye. The first version appended and reversed the column in CSS, which put the focus ring at the bottom travelling upwards against the reading direction (WCAG 1.3.2).

`max` (default 5) drops the oldest. Nothing auto-dismisses by default, so an unbounded queue was a failing poll building a column that ran off the top of the viewport.

### Over a modal dialog it is seen and not heard

The region is a `popover="manual"`, so it reaches the **top layer** and is painted above one of this package's own `Dialog`s — `z-index` cannot do that, and the toast used to paint behind the backdrop.

That fixes the painting and **not** the interaction, which is worth stating rather than glossing: `showModal()` makes everything outside the dialog inert, top layer or not, so the toast cannot be focused and is not announced until the dialog closes. Measured, not assumed. A message that matters while a dialog is open belongs inside the dialog.

## Accessibility

- **The region exists before the message does**, which is the precondition for any of it being announced.
- **One live region owns the message.** The `Alert` inside is `live="off"`; a second one around it announces it twice or with the wrong politeness. (Every `Button` renders a persistent empty `role="status"` of its own, for the same reason this region exists — inert here, since it only ever changes when a button starts loading.)
- **`role="status"`, polite** — an error is conveyed by the severity word, not by interrupting.
- **The name is the region's.** A page may have other live content, so it takes an `aria-label` (default: "Notifications", localized).
- **Nothing races you to a control**: a timed toast has no ✕, and one that stays is under no clock.
- **`aria-atomic="false"`.** `role="status"` implies atomic, and the queue lives in the region — so without it every arrival re-read every message already up, severity words and button names included.
- **The stack never blocks the page**: the region is always mounted, so it takes `pointer-events: none` and gives it back only on the toasts themselves.
- **Reduced motion kills the movement and keeps the change**, which is the package's doctrine and now also what the code does: the entry drops to `fm-fade-in` under `reduce` rather than disappearing entirely, and the exit is opacity-only, so the primitive has no transform to strip. (An earlier version gated the whole animation on `no-preference`, which took the fade away with the travel — a reader who asked for less motion got none rather than a calmer one.)
- **The ✕ is icon-only**, so `Button`'s coarse-pointer rule makes it 44×44 rather than 44 tall and 32 wide.
