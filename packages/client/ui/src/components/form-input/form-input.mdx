# FormInput

FormInput is a labelled text field, already bound to the **form adapter in scope**. It renders the same anatomy as `Field` + `Input`, and takes its control props and its error message from the adapter — so the call site names no form library.

```tsx
<FormAdapterProvider adapter={useMyFormField}>
  <FormInput name="…" label="…" />
</FormAdapterProvider>
```

## Props

There is no `error` prop: the messages come from the adapter as a **list** — a field rarely fails in exactly one way — so they cannot be forgotten or set out of step with the library's own state, and each renders as its own element rather than being joined into one run-on sentence. Every other native prop passes through, and an explicit one at the call site beats the binding.

**What the binding owns is not a prop here at all.** `value`, `defaultValue`, `checked`, `defaultChecked`, `onChange` and `onBlur` are how the field reaches its library — react-hook-form's `register` returns the handlers, the value comes from the library's state — so a call site that won them would not override the binding, it would sever it: the field renders, it types, and it submits nothing. Passing one is a **compile error** that names the lever to use instead, and if the type is bypassed the prop is dropped and dev warns by name.

```tsx
<FormInput name="email" label="Email" onChange={track} />
//                                    ~~~~~~~~ owned by the binding
```

To react to a value change, use your library's own lever — `watch`, `useField`, `subscribe` — which hands you the parsed value rather than a DOM event. To own the handler outright, compose `Field` + `Input` and bind them yourself; that door stays open, and this component adds no markup, so nothing else changes.

A `ref` is the exception: it is the one binding-owned prop that can be shared, so yours is **merged** with the binding's and both receive the node.

## Usage

<Canvas of={FormInputStories.Default} />

### The adapter is a HOOK, not a function

That is load-bearing, and it was measured rather than assumed. With a plain closure in context, the React Compiler caches the provider — react-hook-form mutates its `errors` object in place, so the closure's dependencies look unchanged — the provider never re-renders and **the error never reaches the field, silently**. As a hook it is called inside each bound component, so every field subscribes for itself, and per field rather than per form.

```tsx
const useMyFormField: UseFormField = (name) => {
  const { register, control } = useFormContext();
  const { errors } = useFormState({ control, name });
  const message = errors[name]?.message;
  return { control: register(name), errors: message ? [message] : [] };
};
```

### Names checked against the form

`name` is a `string`, so `name="emial"` compiles and then fails the way an unbound field fails: it renders, it types, and it submits nothing. The form's shape is already a type in your app, so hand it over once and the compiler catches that:

```tsx
// once, beside the form's type
const { FormInput, FormChoice } = createBoundFields<FieldPath<SignupValues>>();

<FormInput name="emial" label="Email" />;
//         ~~~~~~~~~~~~ not a field of SignupValues
```

If you use `@fmmenchi/ui-form-ports`, reach for its kit instead and pass the **values** type — `createRhfForm<SignupValues>()`, `createTanstackFields<…>()`, `createFormikFields<…>()`. It calls this underneath, and derives the paths with your library's own type, so no `FieldPath` reaches your components.

`FieldPath` there is **react-hook-form's own** — use whatever your library offers (`DeepKeys` for TanStack, and a plain union where it offers none). The path syntax for a row belongs to the library too, `guests.0.name` here and `guests[0].name` for Conform, so a path type written in the design system would be wrong for half of them.

It is a factory and not a prop because the type cannot travel any other way: React context carries a value whose type is fixed when the context is created, so no provider can hand a per-form name type to its descendants. There is no runtime — the same components come back, re-typed.

### Repeated fields

An indexed name is still a name, so a row's field needs nothing new:

```tsx
const { fields, append, remove } = useFieldArray({ control, name: 'guests' });

fields.map((row, i) => (
  <FormInput key={row.id} name={`guests.${i}.name`} label={`Guest ${i + 1}`} />
));
```

Counting the rows, adding one, removing one and keying them stays with your library, and that is the honest edge of this shape: **the screen that owns a list names its form library**, while every other screen does not. It is `useFieldArray` above, `getFieldList` + insert/remove intents for Conform, `pushFieldValue` for TanStack, an array in state for Formik. The same markup runs on all four — proved, not asserted, in `ui-ports-validation`'s repeated-fields suite.

### What it cannot do

Binding is by **name alone**, so a per-field validation rule has nowhere to live at the call site — it comes from the adapter, from a schema or a rules map. If you want the rule next to the field, use `Field` and bind it yourself.

## Accessibility

Identical to the unbound anatomy: the label is associated by id, the message is announced through `aria-describedby`, and `aria-invalid` follows it. A control with **no adapter in scope throws** rather than rendering — an unbound field types perfectly well and submits nothing, which is a failure you would meet in production data rather than in development.
