# Tooltip

Tooltip is a short label that appears beside its trigger on hover and on keyboard focus. It is a **description**, not a name: the trigger keeps its own accessible name and gains `aria-describedby`.

```tsx
<Tooltip content="Move to archive">
  <Button aria-label="Archive">Archive</Button>
</Tooltip>
```

## Props

<Controls of={TooltipStories.Default} />

`content` is a **string**, and that is the API refusing something rather than an oversight. A tooltip is reached by hovering or focusing its trigger, never by Tab — so a link or a button inside it could not be operated by a keyboard user at all. Rich, interactive content is a `Popover`.

The trigger is **cloned, not wrapped** (ADR-0016), so the tooltip adds no element of its own to your layout. It must therefore accept a `ref` — the one thing it owes us, and the tooltip warns in development when it does not arrive. Everything else is put on the element directly, so a trigger that picks the props it recognises still opens and is still described. Its own handlers are never touched: the tooltip listens on the node itself rather than passing handlers down, so a trigger with an `onFocus` of its own keeps it — there is nothing to overwrite.

### When not to use one

Read this part first.

| you were going to…             | do this instead                                                                                                                       |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| name an icon-only button       | `aria-label` on the button — a tooltip cannot name a control                                                                          |
| explain a form field           | the `hint` of a `Field`, which is always visible                                                                                      |
| hold something the user needs  | put it on the page; a tooltip does not exist on touch                                                                                 |
| show a link or a button        | a `Popover` — nothing in a tooltip is reachable by Tab                                                                                |
| explain a **disabled** control | a wrapper the tooltip can sit on, or text next to it — a disabled control is not focusable, so the keyboard never reaches its tooltip |

### The delays are not decoration

Opening waits for the pointer to rest (`openDelay`, 400ms); **focus opens immediately**, because unlike a pointer sweeping a toolbar, focus arrives on purpose. Closing waits too (`closeDelay`, 120ms), which is what lets the pointer travel onto the tooltip without it vanishing on the way.

## Accessibility

It owes WCAG **1.4.13 Content on Hover or Focus** three things, and each one is a test:

- **dismissible** — `Escape` closes it, and the focus does not move;
- **hoverable** — the pointer can travel onto the tooltip without it disappearing;
- **persistent** — it stays while the pointer or the focus stays, and never times out.

And four more, from the shape of the component:

- **`role="tooltip"`, referenced with `aria-describedby`.** The surface stays in the DOM while closed, and the reference still resolves even though the browser hides it: a node referenced directly by `aria-describedby` counts as described even when it is not rendered — verified against Chromium's own accessibility tree, where the surface is ignored and the trigger's description is the tooltip's text anyway. A tooltip that is only mounted while open is a description no screen reader ever reads.
- **A press dismisses it.** A click both presses and focuses, so the tooltip closes on the press and does not reopen on the focus behind it.
- **The `Escape` is spent here.** Dismissing the tooltip does not also close the dialog it sits in: one keypress, one dismissal.
- **It says so when it is misused.** In development it warns if `content` only repeats the trigger's `aria-label`, and if the trigger swallowed the ref — two failures that are otherwise completely silent. It does **not** try to tell you the trigger is unnamed: computing an accessible name by hand gets `<img alt>` wrong, and `axe`'s `button-name` already does it properly.

**On touch there is no tooltip**, because there is no hover. That is a platform fact, not an omission — and it is the reason nothing essential may live in here.

### Where it is painted

Where the browser has the Popover API the surface is promoted to the **top layer**, which is what keeps it out of an ancestor's `overflow: hidden` and out of every `z-index` race. Where it does not, the tooltip still appears — just clippable. The layer is the enhancement; the visibility never is (ADR-0021).
