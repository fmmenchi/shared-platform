# Input

A single-line text field on the native `<input>`. It is **transparent** ([ADR-0013](../../../../../apps/docusaurus/docs/adr/0013-form-controls-contract.md)): it forwards its ref and spreads every native prop, and never touches `value`/`onChange`, so it works uncontrolled or controlled and drops into any form library. The design system styles it and presents the invalid state; validation and form-state stay in your app.

## Props

Defaults: `size="md"`, `type="text"`. Every native `<input>` attribute is accepted.

## Usage

### Sizes

`size` matches Button (sm 32 · md 36 · lg 44) so a control and a button line up on the same row.
`lg` meets the 44px touch-target minimum (WCAG 2.5.5 / HIG); `sm`/`md` are for pointer-dense desktop
forms — prefer `lg` where touch is primary.

<Canvas of={InputStories.Sizes} />

### States

The **invalid** look keys off the native `aria-invalid` attribute — the same one your form library
(react-hook-form, Formik, …) already sets. There is no `invalid` prop; the design system only styles
the state, it doesn't compute it.

<Canvas of={InputStories.States} />

### Types

It's a real `<input>`, so `type="email" | "password" | "number" | "date"` and `inputMode` all work.
For **formatted numeric input** (thousands separators, currency, locale decimals), wrap Input with
your own formatter (e.g. `react-number-format`'s `customInput={Input}`) — locale/formatting is a
consumer concern (ADR-0013).

#### `type="date"` is refused — use `DateInput`

This is **the one exception** to the transparency above, and the only `type` this component does not
accept (ADR-0027). `type="checkbox"`, `type="range"` and `type="radio"` still pass straight through
even though `Checkbox`, `Slider` and `Radio` exist, because those are merely duplicative.
`type="date"` is different: it is wrong on the page.

The native date control is right in almost every way — it lines up with a text field to the pixel,
the tokens reach the closed field, `min`/`max` reach `ValidityState`, and on touch it opens the OS
date sheet. What it will not do is **follow the locale you handed `UiProvider`**. Its segment order —
`dd/mm/yyyy` against `mm/dd/yyyy` — comes from the browser, in practice the operating system's
regional format, and nothing on the page can reach it: wrapping it in `lang="it-IT"` moves nothing,
measured. So on a product whose language your app declares, a `Time` or a formatted `Table` cell
reads `12/08/2026` while the field beside it reads the other way round — silently, with no test
going red.

Reach for **`DateInput`** (and `FormDateInput` when it is bound), whose three parts are ordered by the
locale you declared. For per-date rules — "only these slots", "never on a Tuesday" — `min`/`max` are
an interval and not a set; that is `Calendar`.

`type="time"` is untouched: there is no time field to send you to yet, and refusing something with no
replacement would be the same mistake in the other direction.

### Adornments (planned)

Inner icons, a prefix/suffix, or a clear/reveal button live **inside** the field border, so they can't
be siblings of a bare `<input>`. They'll arrive as a separate `InputGroup` wrapper that owns the chrome
with `Input` rendered bare inside (the Radix `TextField.Slot` model) — **not** as `startIcon`/`endIcon`
props on `Input`, which would break its pure-passthrough contract. Until then, place elements outside
the field with your own layout.

## Accessibility

- **Always give it a label.** Wrap it in a `<label>`, or pass `aria-label` / `aria-labelledby`. A
  native input with no associated label has no accessible name.
- **A placeholder is not a label** — it disappears on input and often fails contrast; use it for an
  example value, never as the field's name.
- **Errors:** set `aria-invalid` (your form library does this) and point `aria-describedby` at the
  message element so it's announced with the field. The invalid look is a colour **and** a thicker
  border, so it doesn't rely on colour alone. The design system styles `aria-invalid`; it does not
  invent the error text.
- **`disabled` vs `readOnly`:** `disabled` removes the field from the tab order and drops it from the
  accessibility tree — never use it to lock a **required** field (screen-reader users won't reach it).
  Use `readOnly` for a value that must stay focusable and announced.
- **Controlled or uncontrolled**, focus, and any native attribute pass straight through — the control
  is as capable as the `<input>` it wraps.
