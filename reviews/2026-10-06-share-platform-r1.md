**1. `shareNatively` returns `'shared'` when the reader dismisses the sheet on Windows, so the package's central promise ("dismissal told apart") is false on desktop Chrome and Edge.**

1. Anchor — `packages/client/share/src/lib/native.ts`: "Never rejects: the reader closing the sheet is `cancelled`, and only what is left over is `failed`." and `await navigator.share(content); return 'shared';`. Also `packages/client/share/docs/index.md`: "Closing the native sheet rejects the promise." and "`shareNatively` | Open the sheet; resolves to how it ended, and never rejects."
2. Failure — Chrome or Edge on Windows, reader clicks Share, the Windows share popup opens, reader presses Esc. The promise has already resolved when the popup launched; the outcome is `'shared'`; an app that shows "Thanks for sharing" or counts a share does so for a dismissal.
3. CONFIRMED — MDN `Navigator.share()`, "Windows: The Promise resolves when the share popup is launched"; "Android: The Promise resolves once the data has successfully been passed to the share target". https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share. The specification itself only says the promise resolves once data reaches the target and has no provision for an agent that cannot observe dismissal: https://www.w3.org/TR/web-share/. I did not run it on a Windows machine; MDN is the only source.
4. Fix — narrow the contract in `share.types.ts`, `native.ts` and `docs/index.md`: `'shared'` means "the sheet took the content", not "the reader shared it"; state that on Windows a dismissal is indistinguishable and arrives as `'shared'`. No code change can recover the information.

**2. The X builder uses `https://x.com/intent/post`, which is not the endpoint X documents; the documented one is `https://x.com/intent/tweet`.**

1. Anchor — `packages/client/share/src/lib/share-href.ts`: `` `https://x.com/intent/post?${query({ url, text: text ?? title })}` ``; `docs/index.md` row "`x.com/intent/post?url=<url>&text=<words>`"; `README.md` "// 'https://x.com/intent/post?url=…&text=A%20post'".
2. Failure — the package's stated job is to hold the address the channel publishes. `/intent/post` is an undocumented path; if X stops routing it, every consumer's X link opens a page with no composer, and nothing in the docs backs a bug report.
3. CONFIRMED for the inconsistency with documentation — X's current "Web intent" page gives exactly one URL, "https://x.com/intent/tweet", with parameters `text`, `url`, `hashtags`, `via`, `related`, `in_reply_to` (so `url` and `text` are right): https://docs.x.com/x-for-websites/post-button/guides/web-intent.md. Whether `/intent/post` is served today could NOT be settled: x.com answers HTTP 200 with its app shell for any path (I got 200 for `/intent/post`, `/intent/tweet` and a nonsense `/intent/zzznope` alike), so a probe proves nothing. That it currently works is my recollection, not something verified.
4. Fix — change the path to `/intent/tweet` in the builder, the docs table, the README example and the spec.

**3. `AbortError` is also what the browser rejects with when there is NO share target, and that is reported as `'cancelled'` — "the reader closing it".**

1. Anchor — `packages/client/share/src/lib/native.ts`: `error.name === 'AbortError' ? 'cancelled' : 'failed'`; `share.types.ts`: "`cancelled` is the reader closing it, which is not an error and must not be reported as one."
2. Failure — a device with a share implementation and no available targets: the reader clicks Share, nothing appears, the result is `'cancelled'`, the app (correctly, per the type's doc) stays silent, and the control looks dead. This is the swallowed-real-failure case the package was extracted to remove.
3. CONFIRMED — Web Share spec, `share()`: "If there are no share targets available" → reject with "AbortError"; separately "If the user chose to abort the share operation" → "AbortError". https://www.w3.org/TR/web-share/ ; MDN states the same: "The user canceled the share operation or there are no share targets available." https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share. The other rejections are `NotAllowedError` (permissions policy, no transient activation), `InvalidStateError` (document not fully active, a share already in progress), `TypeError` (data fails validation), `DataError` (target could not be started) — all mapped to `'failed'`, which is right. No source found for an engine that rejects a dismissal with anything other than `AbortError`.
4. Fix — the two cases are indistinguishable by name, so correct the wording: `'cancelled'` = "the sheet did not complete — closed by the reader, or no target to offer"; drop "the reader closing it" as the sole meaning.

**4. A line break in `text` is written into the `mailto:` body as `%0A`, where RFC 6068 requires `%0D%0A`.**

1. Anchor — `packages/client/share/src/lib/share-href.ts`: `` email: ({ url, title, text }) => `mailto:?${query({ subject: title, body: withUrl(text, url) })}` `` with `encodeURIComponent(value)`.
2. Failure — `text: 'First line\nSecond line'` → `body=First%20line%0ASecond%20line%20https%3A…`. A client that follows the RFC strictly may collapse or drop the bare LF.
3. CONFIRMED — RFC 6068 §5: "Line breaks in the body of a message MUST be encoded with "%0D%0A"", example `<mailto:infobot@example.com?body=send%20current-issue%0D%0Asend%20index>`. https://www.rfc-editor.org/rfc/rfc6068.txt. On the brief's other mailto questions, the same RFC settles them in the code's favour: `mailto:?subject=…&body=…` is well-formed (`mailtoURI = "mailto:" [ to ] [ hfields ]`); "all spaces SHOULD be encoded as %20"; and `+` is a literal (`some-delims` includes "+"), so the comment that `URLSearchParams` would put a literal plus in the body is correct. Text and url separated by a space is legal; a line break is a preference, not a conformance point.
4. Fix — in the email builder only, normalise before encoding: `body.replace(/\r\n|\r|\n/g, '\r\n')`. If the url is to sit on its own line, join with `'\r\n\r\n'` instead of `' '` there (not in `withUrl`, which WhatsApp and Bluesky share).

**5. `copyText` documents the rare rejections and omits the common one: in Safari and Firefox a write that is not inside the gesture rejects, so `copyText` after any `await` is always `false`.**

1. Anchor — `packages/client/share/src/lib/clipboard.ts`: "the clipboard is absent on an insecure origin and on a server, and can be denied by permission"; `docs/index.md`: "It refuses on an insecure origin and on a denied permission."
2. Failure — an app does `const short = await shorten(url); if (await copyText(short)) tick()`. Chrome: works (and keeps working once `clipboard-write` is granted). Safari and Firefox: `NotAllowedError`, `false`, every time. Developed on Chrome, shipped broken on iOS, and the docs name two causes that are not this one. "Denied by permission" is also Chromium-only: Firefox and Safari have no such permission.
3. CONFIRMED — MDN Clipboard API, Security considerations: Chromium "Writing requires either the `clipboard-write` permission or transient activation"; Firefox & Safari "Writing requires transient activation" and "The `clipboard-read` and `clipboard-write` permissions are not supported (and not planned to be supported) by Firefox or Safari." https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API ; WebKit bug 244812 "navigator.clipboard.write() rejects with NotAllowedError after an async call" https://bugs.webkit.org/show_bug.cgi?id=244812. Not fetched, so not asserted: the Chromium "document is not focused" rejection, and any case where `writeText` resolves with nothing written — I found no primary source for either.
4. Fix — one sentence in `clipboard.ts` and `docs/index.md`: call it synchronously from the click, with the string already in hand; an `await` before it costs the gesture in Safari and Firefox. The React example already does this.

**7. An empty-string `text` suppresses the `title` fallback, so the words disappear.**

1. Anchor — `packages/client/share/src/lib/share-href.ts`: `text ?? title` (WhatsApp, X, Telegram, Bluesky) and `title ?? text` (Hacker News), followed by `.filter(([, value]) => value)`; `docs/index.md`: "The words that travel with the link are `text`, or `title` where no text was given."
2. Failure — `shareHref('x', { url, title: 'A post', text: '' })` (a CMS field left blank) → `https://x.com/intent/post?url=…` with no `text`: `??` keeps `''`, the filter then drops it, and the title is never used. Same for `{ title: '', text: 'words' }` on Hacker News.
3. CONFIRMED — by reading the code; no external source needed. Not executed.
4. Fix — `text || title` and `title || text`.
